# 技术前瞻排序与参考窗口（任务 C）

> 复现：
> ```
> python -m tools.experiment_lag_calibration --discovery-run-code discover_57acab9520a34c589af8a366
> python -m tools.experiment_lag_calibration --discovery-run-code <run> --theta-sweep 0.25,0.30,0.35,0.40,0.45
> ```
> 运行标识见《13-方法论验证待办》第 5 节。

## 结论摘要

任务 C 的原设想是「前瞻排序 + 参考窗口」四段式：真实里程碑算出成熟度轨迹
$M(t)$ → 找出跨过岗位化门槛 $\theta$ 的时点 $t^*$ → 叠加传导时滞得到参考窗口
→ 按窗口起点全局排序。**实际交付的是前两段与第四段，第三段做不出来。**

| 段 | 状态 |
| --- | --- |
| $M(t)$ 轨迹（真实里程碑日期驱动） | ✅ 已实现 |
| $t^*$ 跨越时点 | ✅ 已实现，25 个 L2 方向中 12 个已跨过 |
| 传导时滞 → 参考窗口 | ❌ **标定失败，不输出窗口** |
| 全局前瞻排序（跨域） | ✅ 已实现，且对 $\theta$ 稳健 |

三点必须随结论一并声明的限制：

1. **不预测未来的跨越。** $M(t)$ 只能算到今天——再往后要假设未来还会发生哪些
   里程碑。因此每个方向只有两种状态：**已跨过**（附真实时点），或**尚未跨过**
   （附距门槛的差值）。没有「预计 X 年跨过」这一类输出。
2. **主语是技术方向，不是岗位。** 措辞为「技术方向 X 已于 Y 跨过岗位化门槛」，
   不是「该岗位将在 Y 出现」。候选依托多个方向，岗位能否成立还取决于这些方向
   是否被同一批雇主组合进同一个职位，这不在本模块的推断范围内。
3. **跨域排序受里程碑整理密度支配。** T1 有 343 条里程碑链接、T5 只有 47 条，
   整理投入多的技术域会系统性排在前面。按既定口径仍做跨域排序（当前范围已收窄
   到具身智能领域，再拆过细），但这一偏差不因排序稳健而消失——**稳健的是名次对
   阈值的稳健，不是名次对整理偏好的稳健**。

## 为什么传导时滞标定不出来

直接测时滞需要 JD 的时间序列，而本项目的 JD 是单次快照（观测窗 2/3 为合成日期）。
替代方案是**截尾观测的双侧夹逼**，只需快照即可：对每个已跨过门槛的方向，记
$e$ 为从 $t^*$ 到今天的已历时长，则

- 今天**已有**岗位需求 ⟹ 传导已完成 ⟹ $lag \le e$
- 今天**尚无**岗位需求 ⟹ 传导未完成 ⟹ $lag > e$

若时滞近似为常数，两组的 $e$ 必须可分。**实测下这个方法退化了**：12 个已跨过
门槛的方向里 11 个已有岗位需求，未到达组只剩 1 个，构不成夹逼。最优切点落在
0 个月、准确率 91.7%——与「里程碑条数」这一对照变量的判别力完全相同，说明可分性
可由整理密度解释，没有超出它。

因此候选卡片的 `foresight.reference_window` 固定为 `null`，
`reference_window_reason` 为 `transmission_lag_uncalibrated`。
**凭空给一个窗口会把先验伪装成结论，宁可只给排序。**

若日后 JD 侧有了真实的跨月采集，这个夹逼会自然恢复判别力——工具已就位，重跑即可。

## $\theta$ 敏感性：排序站得住，时点站不住

$\theta = 0.35$ 是设定值（标定失败的经过见《13》第 5 节）。既然它是拍的，
**排序对它的稳健性就决定了这套判断能不能用**。把 $\theta$ 在 0.25–0.45 之间扫动：

| θ | 跨过门槛 | 已到达 | 未到达 | 与相邻 θ 的排序秩相关 |
| ---: | ---: | ---: | ---: | ---: |
| 0.25 | 16 / 25 | 14 | 2 | — |
| 0.3 | 13 / 25 | 11 | 2 | 0.951 |
| 0.35 | 12 / 25 | 11 | 1 | 0.958 |
| 0.4 | 10 / 25 | 9 | 1 | 0.927 |
| 0.45 | 8 / 25 | 7 | 1 | 0.857 |

相邻 $\theta$ 之间的排序秩相关 **0.857–0.958**——名次基本不随阈值改变。

## 已接入产品的形态

推演每次运行时算一次 L2 前瞻（`_l2_foresight`），把候选依托的各 L2 方向的
判断写进机械卡片的 `foresight` 块：

```json
{
  "schema_version": "candidate_foresight_v1",
  "threshold": 0.35,
  "threshold_origin": "configured_not_measured",
  "reference_window": null,
  "reference_window_reason": "transmission_lag_uncalibrated",
  "directions": [
    {"technology_name": "具身基础模型与VLA", "crossed": true,
     "crossing_month": "2024-01", "peak_maturity": 0.98,
     "milestone_count": 101, "foresight_rank": 2,
     "statement": "已于 2024-01 跨过岗位化门槛（时滞未标定，不给窗口）"}
  ],
  "crossed_direction_count": 2,
  "best_foresight_rank": 1
}
```

`threshold_origin` 与 `reference_window_reason` 是刻意写进数据的：
前台若要展示这个块，必须能读到「阈值是设定的」「窗口没有」这两件事，
而不是只拿到一个看起来很确定的名次。

**当前 227 个候选中只有 100 个带这个块**——候选是一次创建、永久刷新的，
每次运行只重算进入前 100 名的组合。这是《13》第 5 节记录的「候选池混代」问题，
前瞻块的覆盖面受同一个问题限制。
