# 里程碑缺口路径（S6）

> 日期 2026-08-26 · 工具 `extract_milestone_technologies` / `build_milestone_candidates`
> 语料 `biz_milestone_event` 474 条 · 词表 v1.5

## 为什么加这一条路

上游共现路径（论文 + 专利）产出的 A 级里，「强化学习 + 无人机」几乎肯定不是新岗位
信号，而是 **arXiv 的 cs.RO 含大量无人机与低空研究**造成的语料域偏离；
「深度学习 + 移动机器人」则更像抽取粒度问题。两条最高置信度的产出都指不到
任何具体事实，审阅者无从判断。

里程碑事件不同：它是有日期、有主体、人工筛过的具体事件。

| | 上游共现路径 | 里程碑路径 |
| --- | --- | --- |
| 证据 | 两个技术在 N 篇文献里一起出现 | 具体的、有日期的产业事件 |
| 锚点 | 共现累积到门槛的月份 | 事件发生当天 |
| 语料域偏离 | 严重 | 无 |
| 缺口对 | 75 | 18 |
| 落库候选 | 46（A 3 / B 43） | 18（A 2 / B 16） |

**两条路互补，不是替代。** 候选分成 `upstream_signal` 与 `milestone_signal`
两类并列陈列，因为它们的证据能指到的东西不同，混在一起读者无从判断某条的依据强度。

## 判据与算法完全复用

「找缺口对 → A/B/C 分级 → 在缺口图上找团 → LLM 命名 → 落候选」全套沿用
`find_upstream_only_pairs` 与 `build_upstream_candidates`，判据只有一处实现。
抽取输出刻意做成与上游分片同格式（`tech_YYYY.jsonl` + `published` +
`technology_codes`），因此下游一行代码都不用改。

两处刻意的参数差异：

- **`--min-cooccurrence` 默认 1（上游是 3）。** 一篇论文里的偶然共现说明不了什么，
  所以上游要求累积 3 次；而一次有日期、有主体的产品发布或技术突破本身就是一个
  完整事实，要求它重复三次等于把最新的信号全滤掉——里程碑总共才 301 条可用
- **只取 `data_origin_code = source_fact`。** 另有 56 条 `estimated_date` 与
  12 条 `derived_date`，日期是推出来的而非事件携带的，多数被默认到 2026 年。
  锚点日期是本分析的核心量，用推定日期会把信号系统性拉向近期

## 已知瑕疵

- **`具身推理机制 + 具身推理与ECoT` 是同一件事的两种说法**，被生成为候选
  「ECoT具身推理研发专家」。同族近义对的剔除按 L2 归属判定，这两个技术点分属不同
  L2，规则没拦下。试过按名称最长公共子串补一条规则：阈值 ≥4 字能拦下它，
  ≥3 字会误伤「视觉感知与理解 + 触觉感知算法」（共享「觉感知」，而视觉+触觉是
  合理的多模态组合）。**在 n=2 的样本上调阈值是过拟合，因此不加规则**，
  让这条进审核台由人判掉
- **`域随机化 + 检测认证`（2017）、`灵巧操作 + 域随机化`（2018）锚点过老。**
  一个开了八年仍未闭合的缺口，更可能说明这两个技术在招聘上本就不该同现，
  而不是「即将形成岗位」。界面上的「⚠已过期」标注保留，交审阅者判断
- **单条事件即可成立。** A 级两条各只有 1 条依据事件。这是刻意的（见上文
  `--min-cooccurrence`），但意味着**单个事件的代表性完全由审阅者判断**，
  系统不做任何加权

## 平台接入（2026-08-26）

三条发现路径的产出现在走同一套界面。接入时修掉的五处缺陷，都是同一个病根：
**整个前台是围绕「候选来自 JD」这个假设搭的**，而外部证据类的 JD 派生字段恒为 0。

| 位置 | 症状 | 处置 |
| --- | --- | --- |
| 岗位数据卡 | 支撑 JD / 独立企业 / 独立来源 / 学术—产业落差 / 观测窗 / 证据 JD 编号 **全是 0**，真正的证据一个字不显示 | 换成「缺口等级 / 依据事件 / JD 共现 / 能力项」，证据区改列里程碑事件或上游共现对 |
| 岗位数据卡 · 技术方向前瞻 | 对里程碑候选输出「该候选依托的技术方向**没有里程碑证据**，不作前瞻判断」——而它的全部依据就是一条里程碑，自相矛盾 | 该面板读的是 `rel_milestone_technology`（只覆盖 31 个节点）。外部证据类改用候选自身卡片的锚点，面板改名「锚点与参考区间」 |
| 岗位数据卡 · 分类基准 | 套用「参照系是本系统由 JD 聚类得到的岗位库」，而这两类根本没走这条路 | 改用候选自身的 caveat |
| 岗位数据卡 · 能力要求 | 每个技术点后缀「证据 0」 | 外部证据类不显示该后缀 |
| 候选墙 | 每张卡写「支撑 0 份 JD」 | 改为「JD 侧无支撑」 |

另修两处显示错误：卡片里的 `jd_mentions` 与 `evidence_pairs.pair` 存的是**技术编码**
（建卡时 `item["names"]` 装的其实是 codes），界面直接渲染成了「T1.02.10 44 份」。
按卡片自带的同序 `technology_codes` / `technology_names` 对位换名，不改历史数据。

### 图谱：两处会让整类候选静默消失的缺陷

**一、版本号抄错一个字。** 图谱按 `algorithm_version` 判断候选是否为当前版本产物，
而它硬编码的是 `upstream_gap_v1`，实际值是 `upstream_gap_candidate_v1`。
差一个字，46 条上游候选**整批不出现在图谱上，且不报任何错**。
三条路径的版本常量已集中到 `app/modules/discovery/service.py`，工具与图谱都从
那里取，不再各抄一份。

**二、三条路径的分数被放在一个 ORDER BY 里排名额。** 主路径是 0–122 的加权综合分，
缺口分析是 `log1p(共现) × 时间衰减`，上限约 1.2——量纲根本不同。缺口分析的候选
整批排在最后，`limit` 一截就一条不剩（实测 80 个候选节点里两类外部证据为 0）。
反过来把外部证据类全部优先取，主路径又只剩 16 个。改为**各留一半保底、
一侧不够时余额让给另一侧**：当前 80 个节点 = 上游 31 + 里程碑 9 + 已被覆盖 27 +
岗位演化 13。

### 触发方式

前三种模式（综合自动预测 / 技术词定向推演 / 岗位名称推演）由界面发起；
**两条缺口分析路径只能由离线工具跑**——它们要读 JD 之外的语料（论文、专利、
里程碑），且要调 LLM 命名，不适合放在请求里同步执行。
`RunCreatePayload.mode_code` 因此收窄为 `RunnableDiscoveryMode` 三种，
而 `DiscoveryMode` 包含全部五种，推演结果记录库能正确显示这两类运行。

## 不变的局限

与上游路径一样，「这个岗位将来会出现」只能等未来的 JD 检验，本项目时间跨度内
做不到。本路径改善的是**证据质量**，不是结论强度。参考区间仍是外部文献先验，
且 U-3 回测不支持「上游领先招聘」这一前提——界面上照旧标注。
