# 新岗位发现与专项审批实现验收报告

> 日期：2026-08-11  
> 分支：`codex/redesign-from-scratch`  
> 阶段：新岗位发现、机械岗位卡、LLM 表达边界、专项审批与标准 JD

## 1. 阶段结论

本阶段已经建立“自动预测—技术词定向推演—岗位名称推演—记录库—专项审批—正式岗位首版本—标准 JD”的后端闭环。所有运行冻结目标日期和输入快照，候选成熟阶段与审核工作流分别保存，机械事实与 LLM 表达层分别保存。

真实数据库可以完成探索性召回，但当前不能宣称已经发现真实新岗位。原因不是程序未运行，而是正式证据门禁如实发现：

- 已审核技术里程碑为 0；
- 已审批正式岗位版本为 0，无法计算可信的既有岗位覆盖缺口；
- JD 的可靠源时间只覆盖 2026-07 的单一观察窗口，无法证明持续增长；
- 因此真实运行产生的 100 个候选全部为 `potential`，没有任何候选进入 `budding` 或 `emerging`。

这 100 条是供研究人员继续筛选和补证的探索性记录，不是 100 个已发现的新岗位。

## 2. 已实现能力

### 2.1 三类推演

| 模式 | 输入 | 当前输出 |
| --- | --- | --- |
| 自动预测 | 当前技术体系、通过语境校验的 JD 技术证据、已审核里程碑、已审批岗位版本 | 排序候选、机械岗位卡、评分明细、风险标签与专项审批任务 |
| 技术词定向推演 | 1–20 个当前激活技术节点 | 仅分析包含指定技术组合的真实 JD 证据 |
| 岗位名称推演 | 岗位名，可附描述 | 正式岗位、历史候选和真实 JD 标题核验；名称本身不能作为发布证据 |

相同模式、算法版本和输入快照重复执行时返回原运行，不覆盖历史结果。

### 2.2 成熟度与任务缺口

技术成熟度仅消费 `verification_status_code=verified` 且不晚于 `target_date` 的里程碑。系统分别保存：

- 事件类型权重；
- 技术相关度；
- 时间衰减；
- 来源质量；
- 单事件贡献；
- `maturity_raw` 与只用于探索召回的 `maturity_explore`。

没有已审核事件时，`maturity_raw=0`；探索下限不会被用于发布门槛。

产业任务由真实 JD 职责及通过语境校验的技术证据形成。当前数据密度不足以运行稳定的任务社区发现，因此明确使用 `technology_cooccurrence_fallback`，没有伪装为 Leiden 结果。任务分别保存市场支撑、已有岗位覆盖、任务缺口、JD 数、企业数、来源数和证据片段。

### 2.3 候选评分与硬门槛

每个候选独立保存八个正向维度：技术相关度、发布任务缺口、社区凝聚度、市场支撑、技术成熟度、时间增长稳定性、证据完整度和新颖性。单企业、单来源、营销材料、矛盾与未审核技术等惩罚项单独保存。

成熟阶段和工作流严格分开：

- 成熟阶段：`potential / budding / emerging / confirmed`；
- 工作流：`pending / reviewing / needs_revision / approved / rejected / merged`。

阶段判断同时执行数量门槛。高分但只有单企业、单窗口或缺乏应用证据的信号不能进入 `emerging`。

### 2.4 机械事实与 LLM 表达

机械岗位卡保存技术、任务、JD/企业/来源数量、里程碑成熟度、任务缺口、最近岗位重合度和全部证据 ID。表达层只能优化：

- 岗位名称；
- 一句话定义；
- 核心职责归并；
- 形成原因；
- 与已有岗位的差异说明。

表达结果必须引用机械事实卡中存在的 `task:*`、`technology:*` 或 `evidence:*` ID，否则拒绝写入。表达更新不会修改分数、证据数量或成熟阶段。当前尚未配置真实 LLM Provider，真实运行使用机械表达回退；合成测试已验证受约束表达的写入与非法引用拒绝。

### 2.5 专项审批与发布

新岗位审批使用独立队列 `queue_code=job_discovery`，不进入数据中心抽取审核队列。审批通过在同一事务中创建：

1. `origin_type_code=inference_derived` 的正式岗位；
2. 已审批的首个岗位版本；
3. 岗位版本技术要求；
4. 标准 JD。

标准 JD 永久保存 `is_market_evidence=false`，并带有“参考模板”声明，不参与真实招聘量、企业覆盖率、市场支撑或岗位热度计算。仅有名称查询、缺少任务社区、技术关系或证据片段的候选不能发布。

## 6. 后续数据与实现要求

要把候选从探索召回推进到可信发现，需要依次完成：

1. 审核并发布真实技术里程碑，尤其是产品化、企业应用和规模部署事件；
2. 审核上一阶段生成的岗位版本，形成正式岗位覆盖基线；
3. 持续采集至少三个独立观察窗口的 JD，禁止用迁移时间伪造趋势；
4. 建立专家标注集，校准 Top-K、新颖性、多维重合度和阶段阈值；
5. 配置真实 LLM Provider，并在固定机械事实输入上评测名称与职责表达质量；
6. 数据密度满足后，将任务共现回退升级为可评测的任务图社区发现。

下一开发阶段进入三类能力图谱的数据投影与查询接口。本阶段发布的新岗位会复用统一 `JobRole / JobRoleVersion` 模型，因此后续真实 JD 归入该岗位后，可以沿用既有岗位演化流程并同步进入图谱。
