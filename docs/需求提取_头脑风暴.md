> 来源：XH-202621 比赛方案

---

## 一、项目背景与核心痛点

| 痛点 | 描述 |
|------|------|
| 结构性矛盾 | 技术迭代远超人才培养周期，企业"招不到合适的人" |
| 传统方法局限 | 依赖关键词匹配，缺乏对技术趋势的实时感知 |
| 动态关联缺失 | 无法回答"技术A的爆发→新兴岗位B产生哪些新技能需求" |
| 数据质量差 | 招聘数据存在"时滞"、"噪声"、"抄袭"、"通胀"问题 |
| AI幻觉风险 | LLM生成内容可能产生能力"幻觉"，影响图谱科学性 |

---

## 二、核心技术方向

**数据驱动 + 大模型 + 知识图谱**

三大攻关难题：
1. 从海量多源数据中精准发现并定义新兴岗位，更新既有岗位能力要求，构建可动态更新的岗位能力图谱
2. 解决招聘数据的"时滞"、"噪声"与"抄袭"问题，防控AI生成内容"幻觉"
3. 实现高精度简历解析与细粒度人岗差距分析

---

## 三、岗位覆盖范围

立足数字经济，瞄准**新一代信息技术领域**：
- 人工智能
- 大数据
- 智能系统
- 物联网
- （可扩展至相关新兴技术方向）

## 四、核心功能需求（必做）

### 4.1 新岗位发现与定义

**目标**：识别市场上正在萌芽但尚未被标准化、或逐渐兴起的新岗位

**输出要求** — 每个新岗位需生成完整定义：
| 字段 | 说明 |
|------|------|
| 岗位名称 | 标准化命名 |
| 核心职责 | 该岗位的主要工作内容 |
| 必备技能 | 该岗位必须掌握的技能点 |
| 加分技能 | 锦上添花的技能 |
| 典型行业应用场景 | 该岗位在哪些行业有实际应用 |

**交互要求**：
- 支持人工优化（审核/编辑生成的岗位定义）
- 支持动态更新（随着数据变化自动或半自动演进）

---

### 4.2 既有岗位能力动态更新

**目标**：针对现有岗位（如Java开发工程师），识别其能力要求的变化

**输出要求**：
| 字段 | 说明 |
|------|------|
| 能力变化类型 | 新增 / 删除 / 修改 |
| 具体能力项 | 变化的具体技能点 |
| 更新说明 | 为什么发生此变化 |
| 数据源 | 该变化的证据来源 |

**交互要求**：
- 明确标注每条变化的类型（增/删/改）
- 支持人工审核与优化
- 支持动态更新演化
- 贴合企业实际岗位需求

---

### 4.3 新一代信息技术岗位全景图谱

**目标**：可视化展示领域内岗位的能力要求

**粒度要求**：到"技能点"级别

**视图切换**：
- 按**技术栈**切换视图（如前端/后端/AI/数据等）
- 按**级别**切换视图（如初级/中级/高级/专家）

**交互要求**：
- 图谱可视化（节点+边的图结构展示）
- 交互流畅，支持缩放、筛选、搜索

---

### 4.4 人岗匹配度诊断与差距分析

**目标**：用户输入技能数据，系统对比目标岗位图谱，输出差距与规划

**功能点**：

#### 4.4.1 简历解析
- 支持 PDF / Word 等格式
- 提取简历技能要素
- **准确率 ≥ 90%**

#### 4.4.2 匹配分析
- 多维度匹配（技能覆盖度、深度、广度等）
- 输出差距分析（缺失技能项、技能差距程度）
- **匹配准确率 ≥ 90%**

#### 4.4.3 改进建议与路径规划
- 针对性改进建议
- 岗位学习路径规划
- 建议需基于图谱中的技能关联关系

---

## 五、创新性要求（加分/区分度）

### 5.1 多源异构数据清洗与交叉验证

**解决问题**：招聘JD的"时滞"与"噪声"

**机制设计方向**：
- 数据时效性检测（识别过时JD）
- 重复/抄袭检测（JD相似度去重）
- 技能"通胀"识别（区分真实需求与跟风堆砌）
- 多源交叉验证（同一技能在不同数据源中的出现频率、时间趋势）

### 5.2 能力"幻觉"防控

**解决问题**：LLM生成能力项时的准确性

**防控方向**：
- 生成结果与原始数据的事实核验
- 置信度评分机制
- 人机协同审核流程
- 生成约束（Prompt工程 + 结构化输出）

## 六、全流程闭环

系统需实现从数据到应用的完整闭环：

```
多源数据采集
    ↓
新岗位发现与定义 + 既有岗位能力更新
    ↓
能力图谱动态构建
    ↓
简历解析
    ↓
精准匹配与差距分析
    ↓
改进建议与学习路径规划
```

## 十、初步架构思考（待讨论）

### 10.1 数据层
- **问题**：数据从哪来？如何获取多源异构数据？
- **候选方案**：爬取招聘网站 / 使用公开数据集 / 模拟生成
- **存储**：图数据库（Neo4j） vs 关系型数据库 + 图结构表 vs 向量数据库

### 10.2 能力层
- LLM调用：用于JD解析、岗位发现、能力提取、简历解析
- 知识图谱构建：实体抽取 → 关系构建 → 图谱存储与更新
- 数据清洗Pipeline：去重 → 时效过滤 → 交叉验证 → 置信度打分

### 10.3 应用层
- 岗位发现引擎
- 能力更新引擎
- 图谱可视化
- 人岗匹配引擎
- 简历解析器
- 学习路径规划器

### 10.4 关键技术决策点（待头脑风暴）

| 决策项 | 选项A | 选项B | 考量 |
|--------|-------|-------|------|
| 图谱存储 | Neo4j图数据库 | PostgreSQL + JSON/邻接表 | 复杂度 vs 查询灵活性 |
| LLM选型 | DeepSeek | 讯飞星火 / 其他 | 成本、API稳定性、中文能力 |
| 前端可视化 | D3.js / vis.js | ECharts Graph / AntV G6 | 交互需求复杂度 |
| 数据采集 | 实时爬取 | 预置数据集+增量模拟 | 合规性、可控性 |
| 部署方案 | Docker Compose | K8s | 评审便利性 |
| 匹配算法 | 规则+向量相似度 | 图算法（最短路径等） | 准确率 vs 可解释性 |

## 十一、风险与约束

1. **数据合规**：爬取招聘网站需注意合规性，建议以模拟/公开数据为主
2. **LLM成本**：大量JD解析需要控制token消耗
3. **时间约束**：2026年9月5日前提交，需合理分配开发周期
4. **准确率压力**：三项≥90%需要精心设计prompt和验证机制
5. **演示效果**：10分钟视频需覆盖全流程，需提前规划demo场景
