# 新一轮开发计划：打地基 + 移植技术驱动新岗位发现引擎

> **项目**：多源异构数据驱动岗位和能力图谱构建与动态演化分析系统（XH-202621）
> **编制日期**：2026-08-08
> **依据**：《需求提取文档.md》《当前项目能力范围.md》《人岗匹配改进计划方案.md》与 `existing-projects/embodied-job-evolution-lab` 代码审查
> **执行方式**：按阶段执行，每阶段完成后整理文档并提交 commit

## 背景与目标

当前项目的新岗位发现为"聚类驱动"（自下而上聚合存量 JD），存在两个问题：

1. 只能发现**存量 JD 中已成型**的岗位簇，无法回答赛题核心问题"技术 A 的爆发会导致哪些新技能需求/新岗位"；
2. 候选聚类与五要素定义之间缺少"为什么是新岗位"的证据链（成熟度、任务缺口、跨公司信号）。

`embodied-job-evolution-lab` 实现了**技术演化驱动**的新岗位生成系统（技能关键词实体链接 + 技术里程碑成熟度 + 现有岗位任务缺口三维合成），且自带证据链、消融实验与防幻觉约束，与本项目领域完全一致。**本轮开发将其核心引擎移植进统一库体系，替换现有聚类发现作为新岗位发现主路线**（聚类数据保留作对照）。

同时"打地基"：schema 统一归位、数据导入管线标准化、审核闭环对接，为后续人岗匹配画像化改造（见《人岗匹配改进计划方案.md》）预留干净底座。

## 阶段一：schema 归位与规范化（地基）

**目标**：统一建表入口覆盖全部表，新增技术演化域表结构。

- `db/schema.sql` 新增第 10 节"技术演化驱动的新岗位发现"：
  - `technologies`：技术实体（technology_id 如 T1.02 / standard_name / level / aliases_json / 映射 l1_code）
  - `milestones`：技术里程碑（事件 + 日期 + 类型 + technology_links 桥接 JSON）
  - `capabilities` / `tasks` / `role_titles`：算法知识层（能力模板/任务库/任务组→岗位名映射，含 fallback 兜底）
  - `emerging_runs`：预测运行记录（请求/状态/结果 JSON，替代 lab 的 JSON 文件持久化，落统一库）
- `job_definitions` 扩展列：`technology_id` / `scores_json` / `evidence_json` / `job_type`（新兴/演化/已有），`generation_source` 允许 `'emerging'`
- `pipeline/db.py` 的 `init_db` 增加存量库幂等迁移（ALTER TABLE 补列，try/except 容错）
- 验收：`init_db` 对新库与存量 `db/unified.db` 均幂等通过；全量 pytest 不回归

## 阶段二：里程碑与知识库数据导入

**目标**：lab 数据资产迁入统一库，管线化、可重跑。

- 数据文件复制入本项目 `data/raw/`：`milestones_export_6fields.xlsx`（460 条）、`技术词主数据_20260727.xlsx`（L2/L3/L4 技术实体）
- 新增 `pipeline/import_emerging_data.py`（幂等）：
  - 技术主数据 → `technologies` 表（含别名聚合）
  - 里程碑 → `milestones` 表（附 `MILESTONE_BRIDGE` 类目→技术编码桥接映射）
  - 知识层种子（lab `data_importer.py` 的 KNOWLEDGE_* 常量）→ `capabilities`/`tasks`/`role_titles`（含 fallback 模板）
- 验收：脚本重复执行无重复数据；统计输出 technologies/milestones/capabilities/tasks/role_titles 行数

## 阶段三：移植新兴岗位发现引擎（核心）

**目标**：`EmergingJobAlgorithm` 接入统一库，替换聚类发现成为新岗位发现主路线，纳入审核闭环。

- 新增 `pipeline/emerging.py`：
  - `UnifiedRepository`：technologies/milestones 从新表加载；`related_jobs` 基于统一库 jobs.jd_text 别名召回（+ 证据分），替代 lab 私有库
  - `EmergingJobAlgorithm`：成熟度模型、任务缺口评分、任务社区聚类、候选七维评分原样移植
  - Provider 三模式（rule/mock/llm）：llm 模式改用本项目 `pipeline/llm.py`（统一 OPENAI_API_KEY 配置），保留"任务必须携带证据关键词"防幻觉约束
- `backend/api.py` 新增路由：
  - `GET /api/emerging/technologies/search`、`POST /api/emerging/run`（同步执行 + 落 emerging_runs）
  - `GET /api/emerging/runs`、`GET /api/emerging/runs/{run_id}`
  - `POST /api/emerging/submit`：候选岗位五要素写入 `job_definitions`（review_status=pending，带 evidence/scores）——**对接现有 governance 审核队列**
- 新增 `tests/test_emerging.py`：成熟度计算、缺口评分、provider 降级、提交审核链路
- 验收：对新库 T1.02/T1.01/T4.04 三技术各跑一次生成候选；提交后 governance definition 队列可见

## 阶段四：前端新岗位发现页切换

**目标**：`/discovery` 页由聚类卡片切换为"技术驱动发现工作台"。

- `frontend/src/lib/api.ts`：新增 emerging 系列接口类型与函数
- `frontend/src/app/discovery/page.tsx` 重写：
  - 技术搜索 → 实体链接（置信度展示）→ 发起预测 → 候选岗位卡片
  - 候选卡片：得分条（七维分量）、证据链面包屑（技术→能力→任务→岗位）、里程碑/JD 证据、job_type 标签
  - "提交审核"按钮 → job_definitions pending → governance 页闭环
- 聚类发现降级为 `/api/clusters` 保留接口（对照数据，不再作发现页主数据源）
- 验收：`tsc --noEmit` 通过；页面完整走通 搜索→预测→提交审核 旅程
