## 0. 结论速览

**受限口径**(把预测与真值都限制在 v1.1 的 229 个 L3 代码上，这是唯一无混淆的跨版本对比)：

| 指标 | v1.1 | **v1.2** | Δ |
| --- | ---: | ---: | ---: |
| Precision | 0.511 [0.410, 0.611] | **0.585** [0.491, 0.680] | **+0.074** |
| Recall | 0.341 [0.283, 0.399] | **0.444** [0.382, 0.505] | **+0.103** |
| **F1** | **0.409** [0.343, 0.468] | **0.505** [0.440, 0.562] | **+0.096** |
| TP / FP / FN | 95 / 91 / 184 | 124 / 88 / 155 | +29 / −3 / −29 |

**全口径**(含 v1.2 新增的 13 个 L3，真值侧用补标注扩展)：P 0.676、R 0.534、**F1 0.597**。
⚠️ 补标注在看过 v1.2 抽取结果后完成，与被评估系统不独立，该数字**系统性偏乐观**，
不能用作跨版本对比。跨版本比较一律以受限口径为准。

**语料侧覆盖**：有技术要求的 JD 1,678 → 1,712；技术要求行 4,880 → 6,279；
accepted 评估 6,856 → 10,399；需人工复核 735 → 126。

## 1. 改了什么

| 项 | 内容 | 规模 |
| --- | --- | ---: |
| C-1 下线 | 大模型、商业服务、职业教育、AI教育、开源框架、光学组件 | 6 词 |
| C-2 收窄 | 检测、汽车、仓储物流、数据服务、训练场、ACT → 下线宽词形并由窄词形承接；多模态大模型、基础模型、控制系统 → 保留匹配但加 v2 语境规则 | 6 + 3 词 |
| C-3/C-6 新增 | 13 个 L3 技术点、201 个面向招聘语料的表面词 | 见 §2 |
| C-4 ros2 词形 | 补 `ROS2 / ROS 2 / ros1 / rclcpp / rclpy / roscpp / rosbag / nav2` | 171 份 JD 命中 |
| C-5 歧义规则 | 语境窗口整段 → 命中词所在句；语境词带权重需累计 ≥1.0；泛触发词降权 | 规则版本 v2 |
| C-7 升版 | `v1.2`：L3 229→242，L4 1,872→2,073，可匹配别名 1,850→2,039 | — |

**「收窄」被拆成两条原语**：下线宽词形 + 新增窄词形。这样每条改动都能在工作簿里逐行看到，
不需要另一套规则表；只有真正需要语境判断的三个词才保留歧义规则。

### 治理链路（可复现）

词表的权威来源是工作簿，所以升版不改数据库，而是「基线工作簿 + 变更集 → 新工作簿 → stage → import」。
变更集是仓库内的 JSON，整条链路只依赖仓库文件：

```bash
python backend/tools/build_taxonomy_workbook.py \
  --base 'data/source/20260810/core/技术词主数据_20260727.xlsx' \
  --changeset data/governance/taxonomy_v1_2_changeset.json \
  --out 'data/governance/技术词主数据_v1.2.xlsx'
```

渲染器会挡住三类错误：新增词与既有词重复、挂载的 L3/L2 不存在、同一词形跨节点重复
（首次运行即拦下 8 条重复，其中 5 条是「v1.1 已有该窄词形」——说明只需下线宽词即可）。

## 2. 逐项改动的贡献拆解

受限口径下 v1.1 → v1.2 的每一条预测变化，按改动类别归因：

| 改动类别 | 新增 TP | 新增 FP | 减少 TP | 减少 FP |
| --- | ---: | ---: | ---: | ---: |
| 新增表面词（C-3/C-4/C-6） | **31** | 17 | 0 | 0 |
| 下线过宽词（C-1/C-2） | 0 | 0 | 2 | **19** |
| 歧义规则 v2（C-5） | 0 | 0 | 0 | 1 |
| **合计** | **31** | **17** | **2** | **20** |

**净效果：TP +29、FP −3。** 召回的提升几乎全部来自新增表面词，精确率的提升几乎全部来自下线过宽词——
两类改动各自解决了窗口 A 诊断出的两个问题，互不重叠。

### 2.1 下线消除的误报（按原命中词）

`检测` 8、`大模型` 5、`职业教育` 2、`ACT` / `控制系统` / `AI教育` / `汽车` / `商业服务` / `仓储物流` 各 1。
下线同时误伤 2 条真阳（`检测`/`控制系统` 在少数 JD 里确实指向对应技术点），代价可接受。

### 2.2 新增词带来的真阳（受限口径 top）

`IMU` 6、`MuJoCo` 3、`ROS2` 3、`Jetson` 2、`Orin` 2、`Sim2Real` 2、`PyBullet` 2、`外参标定` 2、
`STM32` 2、`单片机` 2，其余 `Isaac Gym/Lab/Sim`、`RTK`、`UWB`、`Kalibr`、`WBC`、`Gazebo`、`时间同步` 等各 1。

这些词全部挂在**既有**的 L3 上——也就是说，v1.1 的问题不只是「缺技术点」，
更是**既有技术点的表面词收错了方向**：节点存在（T2.04.01 惯性测量单元、T4.03.05 仿真平台），
但表面词是学术长术语，招聘语料里写的是 `IMU`、`MuJoCo`。这印证了窗口 A 对 L4 层的更正判断。

### 2.3 新增词引入的误报（17 条）

| 命中词 → 节点 | 条数 | 判读 |
| --- | ---: | --- |
| `汽车电子` → T7.01.04 汽车制造 | **6** | ❌ **映射错误**：汽车电子（车载电子部件/行业方向）≠ 汽车制造 |
| `ROS2` → T5.01.01 ROS | 2 | 标注漏标（JD 明确写了 ROS2） |
| `IMU` → T2.04.01 | 2 | 标注漏标（JD 明确列了 IMU 传感器） |
| `AGV` → T3.03.08 | 2 | 1 条是销售岗（属非技术岗过滤问题，窗口 B） |
| `NPU`/`FPGA`/`MoveIt`/`3DGS`/`Isaac Sim+MuJoCo` | 各 1 | 边缘或标注漏标 |

**已知缺陷：`汽车电子` 映射错误。** 它是新增词里最大的单一误报来源。按版本纪律不回改已发布的 v1.2
（在评估集上发现的问题若立刻回改同一版本，就是对评估集调参），已登记在
`data/governance/taxonomy_v1_2_changeset.json` 的 `pending_next_version` 中，下一版下线。
修掉后受限口径精确率约 0.585 → 0.602。

## 3. 评估口径与方法学声明

### 3.1 为什么必须有「受限口径」

`annotator_C` 的 `expected_l3_codes` 是在 v1.1 的 229 个代码空间里写的。v1.2 新增了 13 个 L3，
这些代码在真值侧**永远缺席**——直接对照会把新技术点的每一次正确命中都算成误报。
naive 全口径对比给出 P 0.451（看起来精确率下降了），而实际上那 63 条「误报」里绝大多数是
标注空间缺失，不是抽取错误。

受限口径把预测与真值都交到 v1.1 的 229 个代码上，两版在完全相同的判定空间里比较，
这才是可比的数字。

```bash
python backend/tools/evaluate_extraction_quality.py \
  --package docs/reports/annotation_package/jd_annotation_batch_001.annotator_C.v1_2.json \
  --restrict-codes docs/reports/annotation_package/v1_1_l3_codes.json
```

### 3.2 补标注的偏差声明

为给出全口径参考值，对 13 个新代码做了补标注（`annotator_C.v1_2_extension.json`，69 条新增期望，
覆盖 34 份样本），原有 v1.1 代码上的判定逐字未动。补标注遵循原标注的既有口径：
非技术岗期望集合保持为空、泛义用词（「输出量化报告」的量化、「产品生命周期」）不计入。

**但补标注是在看过 v1.2 抽取结果之后做的，与被评估系统不独立。** 全口径的 F1 0.597
因此偏乐观，只能说明「新增技术点在语料中确有依据」，不能作为性能声明。

### 3.3 继承自窗口 A 的局限

`annotator_C` 为单人标注、标注者为 AI 助手且非领域专家、未经双人仲裁。
本报告的全部数字**仅供版本对比，不得作为论文金标准**。

## 4. 仍未解决的问题（交给下游窗口）

1. **非技术岗仍是误报主体**：40 份非技术岗产生 37 条误报（v1.1 是 46 条），精确率仍为 0.000。
   词表治理只消除了其中 9 条，剩下的必须靠**窗口 B 的岗位过滤**。
2. **T7 域仍然很差**（受限全口径 P 0.091）：T7 是场景/行业域，本身与「技术点」的口径就不匹配，
   建议在论文口径里明确 T7 不参与技术能力测量，而不是继续修词。
3. **仍有召回缺口**，且多为词形差异而非缺节点：
   - 「压缩量化」「量化」单用（词表只收了「模型量化」）——3 份样本漏报
   - 「正向/逆向运动学」（词表收的是「正运动学/逆运动学」，差一个「向」字）
   - 「机器人运动学」这类以泛称出现的要求
4. **本语料零命中的新增词 32 个**（`rclcpp`、`CycloneDDS`、`LibTorch`、`型式试验` 等）。
   保留但记录在案：它们是合法词汇，只是这批 3,718 份 JD 里没出现；
   若下一批语料仍零命中，应按 C-6 的原则下线。

## 5. 明确不收的内容（范围边界）

按任务书第 2 节边界 1「不要为提升整体召回把词表扩到通用工程领域」，以下候选**主动不收**，
已写入变更集的 `scope_exclusions`：

| 不收内容 | 理由 |
| --- | --- |
| 电池/BMS/热管理/结构设计 | 通用机电工程；《L3覆盖盲区报告》本就标为「范围争议项」 |
| PCB/原理图/EMC/RTL/ISP/HALT | 通用硬件工程实践，超出具身智能技术口径 |
| CVPR/ICRA/NeurIPS 等会议词 | 资质信号而非技术点 |
| 整机在售型号（宇树 G1/H1 等） | 型号追踪不是研究目标，且迭代快会让词表迅速过期 |
| `robot`/`robotics` 英文泛称 | 触发面过宽，等价于不做区分 |

这批内容占《L3覆盖盲区报告》所列「可补 320 份零证据 JD」中的大部分，
也解释了为何本次 JD 覆盖只从 1,678 升到 1,712——**这是有意的取舍，不是执行不到位**。

## 6. 复现步骤

```bash
# 1. 渲染 v1.2 工作簿（纯仓库文件，不依赖数据库）
python backend/tools/build_taxonomy_workbook.py \
  --base 'data/source/20260810/core/技术词主数据_20260727.xlsx' \
  --changeset data/governance/taxonomy_v1_2_changeset.json \
  --out 'data/governance/技术词主数据_v1.2.xlsx'

# 2. 暂存并发布（容器内；--no-deps 避免触发 bootstrap 重跑 v1.1 全链）
docker compose run --rm --no-deps backend python -m tools.stage_workbook \
  --file '/srv/data/governance/技术词主数据_v1.2.xlsx' \
  --storage-key 'data/governance/技术词主数据_v1.2.xlsx' \
  --importer-code taxonomy_xlsx_v1 --mapping-code technology_taxonomy_v1_2 \
  --mapping-version 1.2.0 --classification project_internal \
  --external-key 'L1技术域=L1编码' --external-key 'L2技术类=L2编码' \
  --external-key 'L3技术点=L3编码' --external-key 'L4技术词=技术词'

docker compose run --rm --no-deps backend python -m tools.import_taxonomy \
  --mapping-code technology_taxonomy_v1_2 --version-code v1.2 \
  --version-name '具身智能技术词主数据v1.2' \
  --effective-date 2026-08-18 --domain-version v1.2

# 3. 在既有 JD 上按新词表重抽取（v1.1 的抽取结果与历史解析运行不受影响）
docker compose run --rm --no-deps backend python -m tools.reextract_requirements --taxonomy-version v1.2

# 4. 解析
docker compose run --rm --no-deps backend python -m tools.parse_jobs \
  --taxonomy-version v1.2 --target-date 2026-08-31

# 5. 刷新标注包的抽取快照并评估
docker compose run --rm --no-deps -v "$PWD/data/annotation:/srv/out" backend \
  python -m tools.refresh_annotation_extraction \
  --package /srv/data/annotation/jd_annotation_batch_001.annotator_C.json \
  --parse-run-code <上一步的 run_code> --out /srv/out/annotator_C.v1_2.json

python backend/tools/evaluate_extraction_quality.py \
  --package docs/reports/annotation_package/jd_annotation_batch_001.annotator_C.v1_2.json \
  --restrict-codes docs/reports/annotation_package/v1_1_l3_codes.json
```

## 7. 附：为支撑升版而做的结构改动

词表升版原本**根本跑不通**——技术词表面匹配只在 JD 导入时执行一次，
`biz_job_requirement` 也没有词表版本维度，换版要么改不了、要么只能就地覆盖并毁掉历史解析运行。

| 改动 | 说明 |
| --- | --- |
| 迁移 `20260818_0016` | `biz_job_requirement` 加 `taxonomy_version_id`，唯一约束改为版本内唯一。**注意**：MySQL 拿唯一索引当外键支撑索引，新约束改以 `taxonomy_version_id` 打头后必须先补 `job_posting_id` 单列索引，否则删旧约束会报 `needed in a foreign key constraint` |
| `app/modules/job/extraction_service.py` | 抽取逻辑从 `JobImportService` 内联剥出，首次导入与换版重抽取共用一份实现 |
| `tools/reextract_requirements.py` | 按指定词表版本在既有 JD 上重抽取，幂等；`--replace` 只清该版本 |
| 读取侧版本收敛 | `api/jobs.py`（3 处）、`talent/service.py`（2 处）原先无版本过滤，多版并存后会重复计数/重复命中，已收敛到 active 版本 |
| 歧义规则按版本落行 | 规则挂具体 `technology_node_id`，节点逐版本独立，`rule_code` 带 `@版本` 后缀避免撞唯一键；停用只作用于本版本的规则行 |
| `run_code` 纳入规则版本 | 规则行为变了但 `PARSER_VERSION` 没变时，重放缓存会串味 |

### ⚠️ 一处需要其它窗口注意的副作用

`docker compose run backend ...` 会触发 `bootstrap` 依赖链，从而**用新的 v2 歧义规则重跑一遍 v1.1 全链**。
本次因此多出解析运行 `jdparse_5ce029035f848ee65100eb60`（v1.1，parse_run_id=4）与聚类运行
`cluster_27de1709f5694ac1ba8733dc`（clustering_run_id=9）。它们是合法的 v1.1 重跑，不是脏数据，
但**「最新聚类运行」已经从 8 变成 9**——窗口 D/E 如果按「最新运行」取数，请确认取到的是预期的那一次。
后续跑一次性命令请一律加 `--no-deps`。
