## 1. 标注任务

对 `jd_annotation_batch_001.json` 中的每份样本,填写三个字段:

| 字段 | 填什么 |
| --- | --- |
| `expected_l3_codes` | **你认定该 JD 应当抽出的全部 L3 技术点代码**(参照 `l3_reference.json`,229 个) |
| `role_type` | 四选一:`embodied_algo`(具身算法)/ `hardware`(硬件)/ `engineering`(工程)/ `non_technical`(非技术) |
| `annotator_notes` | 不确定、有争议或词表没有对应节点的技术,写在这里(自由文本) |

**对照基准**:`current_extraction`(已冻结的 run 3 快照,含 accepted 与 needs_review 及命中词)。
标注时**不要**参考它——先独立标完 `expected_l3_codes`,再对照,避免锚定偏差。

## 2. expected_l3_codes 判定规则

1. **计入**:职责/任职要求中明确要求掌握、使用、研发、维护的技术。
2. **不计入**:仅在「公司业务背景」「产品介绍」「福利」中泛泛提及的技术;
   与岗位核心工作无关的顺带一提。
3. **工具与平台**:编程语言/框架(python、pytorch 等)按现行词表口径**不计入**
   (词表明确不含通用编程词;此口径争议已记录在 1.2 报告,本批次先按不计入执行,
   有异议写 notes)。
4. **整机/场景词**:岗位本体(如「人形机器人结构工程师」标题里的人形机器人)
   若同时是其工作对象,计入对应 L3;纯行业背景词不计入。
5. **零技术 JD**:非技术岗或与具身智能无关的岗位,`expected_l3_codes` 填 `[]`。
6. **词表缺失**:JD 明确要求但 `l3_reference.json` 找不到合适 L3 的技术,不硬凑,
   写入 notes(格式:`MISSING: 技术名 - 出现位置摘要`),这类将汇入 1.2 缺口清单。
7. 每份 JD 预计 2–8 个;超过 10 个时自查是否违反规则 2。

## 3. role_type 判定

- `embodied_algo`:感知/定位/规划/控制/学习/VLA/世界模型等算法研发岗
- `hardware`:整机/结构/电控/传感器/关节/驱动等硬件研发岗
- `engineering`:部署/测试/数据采集/平台工具/嵌入式实现等工程岗
- `non_technical`:销售/产品/运营/职能/教研等

拿不准时按「JD 中技术深度要求的主体」归类,并写 notes。

## 4. 双人标注流程

1. 两名标注者**独立**填写,输出各自副本:
   `jd_annotation_batch_001.annotator_A.json`、`jd_annotation_batch_001.annotator_B.json`
   (复制原文件后填写;除三个待填字段外不得改动任何内容,包括 current_extraction)。
2. 逐份对比;`expected_l3_codes` 不一致处由两人讨论裁决,形成
   `jd_annotation_batch_001.gold.json`(裁决版,`annotation_status` 置 `adjudicated`)。
3. 评估脚本默认读 gold;仅有单标注时直接读单份文件,并在报告声明「单人标注」。

## 5. 评估

标注回填后运行(在 backend 目录):

```bash
python tools/evaluate_extraction_quality.py \
    --package ../docs/reports/annotation_package/jd_annotation_batch_001.gold.json
```

输出:总体与分层(按 role_type、按 primary_domain)的 Precision / Recall / F1,
附 JD 级 bootstrap 95% 置信区间;`--include-review` 可切换 needs_review 是否计入预测侧。
脚本已用合成标注数据自测(见 `--self-test`),数字口径见脚本内文档字符串。
