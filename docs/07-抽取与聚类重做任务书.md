## 1. 一句话背景

项目已跑通「JD 导入 → 技术抽取 → 岗位聚类 → 岗位版本演化 → 新岗位发现 → 人岗匹配」全链路，
但**最上游的技术关键词抽取存在结构性缺陷**，导致下游岗位画像稀疏、聚类退化、新岗位判别失效。
本轮工作的目标是修复抽取与聚类，使下游的研究结论建立在可信数据上。

**在抽取质量评估完成之前，不要调聚类参数，也不要基于现有技术证据得出研究结论。**

## 3. 研究目标（决定技术取舍的上位约束）

本项目同时是一篇论文的实证基础。论文有三条候选主线，**当前倾向 B+C 为主、A 为方法论保障**：

| 方向 | 内容 | 时间维度 | 状态 |
| --- | --- | --- | --- |
| **A** | 岗位能力演化的**可靠测量**（多代隔离、簇谱系、采样量混淆告警、可重放） | 岗位侧时间不可靠 | 机制齐全，降级为方法论保障 |
| **B** | 技术成熟度（里程碑真实时间序列）与岗位能力结构的**关联分析** | 仅技术侧用时间 | 数据条件最好 |
| **C** | 基于结构的**能力缺口识别 / 新岗位发现** | 不用时间 | 受抽取质量阻塞 |

### 3.1 已确定的方法论立场（不要推翻）

1. **传导时滞不做实证。** 岗位首次涌现时间在本数据条件下**原理上不可观测**（左截断问题：
   从不完全抽样无法证明"此前不存在"）。外部参考文献把"首次被采集到"当作"首次出现"，本项目
   不沿用。时滞先验参数已保留在 `TECHNOLOGY_CLASS_LAG_PRIOR`，但**必须标记为 `reference_prior`，
   不得当作实测值引用**。
2. **时间维度只用于技术侧。** 论文发表日、专利申请日、产品发布日可考；JD 采集时间不可考。
3. **LLM 只做表达层，不进机械决策路径。** 详见第 6 节约束。

## 4. 根因诊断（已完成，附证据）

### 4.1 完整因果链

```
L4 表面词层来自学术文献语料，与招聘语料词汇不重叠
   → L4 完全空转（1,872 个词命中次数为 0）
   → 全部证据仅来自 L3 层（111/229 个节点）
      + L3 部分表面词过宽（"大模型"→ VLA端到端大模型）→ 误报
      + L3 对工程实践类技术覆盖不足 → 漏报
         → 有证据 JD 仅 41.6%，中位数仅 2 个技术词，且部分是错的
            → 聚类能力通道（权重 0.25）对多数 JD 失效
               → 78% 单例簇、簇大小中位数 1
                  → 岗位画像稀疏（58 个岗位仅 2 个技术词，32 个仅 1 个）
                     → 覆盖率测量只有 0/0.5/1.0 三个取值
                        → 新岗位判别失效（91/100 候选覆盖率 = 1.0）
```

### 4.2 关键证据

**证据 1：L4 层完全空转**

```sql
-- 1,872 个 L4 表面词，命中次数全部为 0；7,591 条证据 100% 来自 L3
select n.level_code, count(*) from biz_job_requirement r
join biz_technology_match_assessment t using(job_requirement_id)
join md_technology_node n on n.technology_node_id=r.technology_node_id group by 1;
-- 结果：L3 7591 条 / 111 个节点；L4 无记录
```

**证据 2：L4 词表是论文术语，不是招聘用语**

1,872 个 L4 词中 393 个超过 15 字，样例：

```
ACE-Brain-0.5统一具身基础模型架构
CodeGraphVLP语义图状态非马尔可夫VLA架构
GR00T N1.7 Cosmos-Reason双层VLA架构
CLAP LIBERO成功率与训练效率
```

### 4.3 聚类自身的实现缺陷（次要，但需一并处理）

算法在 `backend/app/modules/clustering/algorithm.py`，为**单遍贪心增量聚类**：
按 (标题, job_code) 排序遍历，相似度 ≥ `assign_threshold`(0.36) 则加入，否则自建新簇。

| 缺陷 | 说明 |
| --- | --- |
| `scenario` 通道恒为 0 却占 8% 权重 | 有效满分只有 0.92，阈值 0.36 被隐性抬高 |
| `level` 通道二值化 | 初级 vs 中级得 0 分，与"完全无关"等价，7% 权重在制造噪声 |
| 无迭代重分配 | 成员进簇后不再调整，质心漂移导致早期成员不再属于该簇 |
| `cosine` 无交集直接归零 | 无平滑，能力通道对稀疏 JD 恒为 0 |
| 低信息量 JD 参与聚类 | 技术词 <2 的 JD 注定匹配不上，直接制造 1,630 个单例簇 |

- **验收**：产出带置信区间的指标报告；明确声明标注者身份与是否双人标注

### 任务组 4：聚类重做

**前置**：任务组 2、3 完成（输入质量确定后才能标定参数）。

#### 4.1 相似度权重修正

- `scenario` 通道：实现该通道，或将其权重重新归一化到其余五通道
- `level` 通道：二值改为有序距离（相邻级别给部分分）
- 修正后需重新标定 `assign_threshold` / `grey_threshold`

#### 4.2 低信息量 JD 归池

- 技术词 < N 的 JD 不参与聚类，进待治理池
- **验收**：单例簇数量大幅下降

#### 4.3 迭代重分配（解决质心漂移）

- 在现有相似度函数上实现 Lloyd 式迭代：重算质心 → 全局重分配 → 直到稳定
- 终止条件：本轮重分配数 < 总数 1%，或达最大轮次（建议 10）
- 每轮重分配数量写入 `quality_metric_json`，收敛过程可审计
- **注意**：重分配会改变成员集合，而簇谱系依赖成员 Jaccard ≥0.55 匹配。
  需验证收敛后 `continued` 谱系不会大面积断裂

#### 4.4 核心能力定义与加入门槛

**设计已确定（经讨论）**：

- 簇的核心能力 = 技术词的**加权出现率** ≥ θ 的集合，
  权重 = 该成员与质心的相似度（阻尼：边缘成员对"什么是核心能力"话语权更低）
- 加入门槛：候选 JD 需覆盖核心能力集合的 ≥ ρ 比例，**且**总相似度过阈值
- 初值建议 θ=0.5、ρ=0.5，**跑完看分布再定**，不要先拍死
- **收敛陷阱**：硬门槛会破坏 Lloyd 的单调收敛。被所有簇拒绝的 JD 落入灰区池，
  不强行分配；必须设最大轮次并检测振荡

**为什么核心能力用机械定义而非 LLM**：反馈回路问题（核心能力从成员算出，
又用于决定成员）在单遍设计中确实存在，但**全局重分配收敛后在数学上消解**——
收敛条件即"每个成员到自己簇质心的相似度 ≥ 到任何其他簇质心"。
加权投票用于阻尼迭代**过程中**的中间态污染。

- **验收**：单例簇比例、簇大小中位数、平均一致性三项均显著改善；
  收敛过程可复现（同输入同参数同结果）

## 6. 必须遵守的约束（违反会破坏既有设计）

1. **LLM 不得进入机械决策路径。** 不得由 LLM 决定簇归属、技术编码、评分或分档。
   LLM 的合法位置：(a) 离线批处理后 materialize 为带版本的数据；(b) 表达层改写
   （岗位名称、定义、解释）。参考 `docs/02` 的数据约束第 1 条。
2. **可重放性。** 同样输入 + 同样算法版本 + 同样参数 → 必须得到同样结果。
   任何影响输出的输入变化都必须进 `input_snapshot_hash`
   （曾有 bug：改 JD 采集时间却命中重放缓存，已修并有回归测试）。
3. **算法行为变更必须升 `ALGORITHM_VERSION`**，否则历史运行的重放缓存会串味。
4. **参数不得硬编码**，应进 `DEFAULT_PARAMETERS` 并写入 `run.parameter_json`。
5. **证据必须逐字可定位。** 技术证据须能追溯到 JD 原文的具体片段。
6. **合成数据必须显式标记。** 当前 JD 观测窗中 2/3 为合成日期
   （`time_quality_code='synthetic_window_spread'`），任何基于观测窗的结论
   都必须声明这一点。里程碑中 48 条为估算年份（`data_origin_code='estimated_date'`）。
7. **不要在 `main` 或 `codex/redesign-from-scratch` 上直接提交。**

## 7. 已知陷阱与操作提示

| 陷阱 | 说明 |
| --- | --- |
| **镜像未重建** | `migrate`/`bootstrap`/`backend` 是三个独立镜像但共用 `./backend` 构建上下文。只 `build backend` 会导致 migrate 停留在旧代码报 `Can't locate revision`。需三个一起 build |
| **`docker cp` 不持久** | 容器重建即回退，代码改动必须重建镜像 |
| **`ruff format` 误伤** | 仓库有 17 个文件未按 ruff format 规范，跑 `ruff format app/` 会产生大量无关 diff。CI 只跑 `ruff check`，**只格式化自己改动的文件** |
| **迁移的 DDL 自动提交** | MySQL 上 `ADD COLUMN` 即使迁移后续失败也会留下残留列，需手工回退到干净点再重跑 |
| **SQLite/MySQL 迁移差异** | SQLite 不支持 `UPDATE 表 别名` 语法；约束调整需 `batch_alter_table`；MySQL 上删旧唯一索引前需先建新索引（外键依赖） |
| **重新解析不继承 LLM 回写** | 首代 7,057 条 accepted，重解析后 6,856 条——少的 201 条是 DeepSeek 回写结果。换代后需重跑 `tools/reassess_technologies_llm.py` |
| **推演去重** | 候选按 `candidate_key`（模式+技术组合）去重，已处置的组合不再提出。测试时若发现"新建 0 个"是正常的去重行为，不是失败 |
