# 具身智能岗位与能力图谱系统——完整开发计划

> 计划版本：v1.0
>
> 计划基线日期：2026-08-10
>
> 正式开发启动条件：2026-08-11 收到原始 XLSX 数据并完成只读接收检查
>
> 目标交付日期：2026-09-05
>
> 开发分支：`codex/redesign-from-scratch`

## 1. 计划目标

本计划用于把已经定稿的需求、总体设计、后端数据流、新岗位算法和目标数据库结构实现为可以真实运行、评测和演示的挑战杯项目。

最终系统必须打通两条纵向闭环：

```text
多源采集
→ 原始文档与版本
→ JD/技术词/里程碑抽取
→ 证据校验与审核
→ 正式 JD 和岗位聚类
→ 既有岗位演化 / 新岗位发现
→ 专项审批与岗位版本
→ 三类能力图谱
```

```text
多模态简历输入
→ 文本解析与技术词标准化
→ 2–8轮自适应追问
→ 求职者画像版本
→ 岗位匹配
→ 差距解释
→ 发展路径
```

计划执行遵循以下优先级：

1. 真实证据闭环优先于页面数量；
2. 数据版本和可追溯优先于算法复杂度；
3. 可解释基线优先于不可验证的高分模型；
4. 纵向完成一个真实案例后再扩展横向覆盖；
5. 任何生成内容不得污染真实市场证据。

### 2.1 已完成资产

### 2.2 正式启动条件

收到原始 XLSX 后首先完成数据接收门禁，不直接导入正式表。至少确认：

- 文件列表、文件大小、修改时间和 SHA-256；
- 工作表名称、行列数、表头和数据类型；
- 技术词 L1–L4 与 T1–T7 字段真实语义；
- JD 原文、企业、来源链接、发布时间和采集时间；
- 里程碑名称、类型、日期、主体、来源和技术关系；
- 是否包含现有岗位、岗位职责、能力、别名和历史版本；
- 空值、重复、冲突编码、公式单元格和合并单元格；
- 个人信息、许可证和使用范围。

### 2.3 启动阻断项

以下问题没有明确处理方案时，不进入批量正式导入：

- 无法判断 L 层级与 T 领域的字段语义；
- JD 缺少原文且无法回到来源；
- 里程碑只有来源名称而没有可验证证据；
- 生成岗位或生成 JD 与真实招聘 JD 混在同一数据集且无法区分；
- 文件含有敏感个人信息但没有授权；
- 编码关系存在大规模循环、悬挂或重复主键。

## 3. 技术实施基线

### 3.1 总体形态

首期采用模块化单体 API + 异步 Worker：

| 层 | 建议实现 |
| --- | --- |
| 前端 | React 19 + TypeScript + Vite，保留现有 Mock 页面并逐页接入 API |
| API | Python + FastAPI + Pydantic |
| ORM/迁移 | SQLAlchemy 2 + Alembic |
| 主数据库 | MySQL 8 |
| 异步任务 | Redis + Worker；具体库在脚手架阶段固定 |
| 调度 | 首期使用 Worker 定时调度，保留替换接口 |
| 对象存储 | S3 兼容接口；本地开发可使用 MinIO或文件适配器 |
| LLM | OpenAI 兼容网关适配器，保存模型和 Prompt 版本 |
| OCR/文档 | PDF、TXT、DOCX、图片分别通过适配器接入 |
| 向量 | 首期独立适配器；可先用数据库外的本地索引验证 |
| 图谱 | 关系库投影 + 成熟前端图谱引擎，不首期引入独立图数据库 |
| 测试 | pytest + API集成测试 + 前端单测 + 浏览器端到端测试 |
| 部署 | Docker Compose，包含前端、API、Worker、MySQL、Redis和对象存储 |

| 单元测试 | 归一化、技术词匹配、成熟度、评分、向量、状态机 |
| 仓储测试 | MySQL约束、版本、幂等、事务和Outbox |
| 集成测试 | 导入、采集、抽取、审核、聚类、推演、匹配完整链路 |
| 契约测试 | OpenAPI请求响应、游标分页、任务状态和错误码 |
| 评测测试 | JD、简历、匹配和新岗位专家标注集 |
| 端到端测试 | 浏览器中完成两条纵向闭环 |
| 非功能测试 | 性能、安全、隐私、恢复和可重复部署 |

### 6.2 每个任务的完成定义

每项开发任务同时满足以下条件才可标记完成：

- 代码实现完成；
- 数据迁移或表变化已记录；
- 单元/集成测试通过；
- 错误和空态可处理；
- 关键日志与审计存在；
- 输入输出绑定数据版本；
- 前端需要的接口文档已更新；
- 相关设计文档和需求追踪已同步；
- 没有把 Mock 或生成内容混入正式证据。

## 7. 数据到位后的首日执行清单

2026-08-11 收到 XLSX 后按以下顺序执行：

1. 不打开覆盖保存，不修改原文件；
2. 复制到受控原始数据目录并计算 SHA-256；
3. 记录发送来源、接收时间和文件说明；
4. 列出全部工作簿、工作表、行列数和表头；
5. 抽样查看公式、合并单元格、隐藏表和日期格式；
6. 生成空值率、唯一值、重复行和类型分布；
7. 核对技术词编码和父子关系；
8. 核对 T1–T7 是独立领域还是被误用为 L1；
9. 核对 JD、里程碑和岗位定义的事实来源；
10. 与目标表逐字段映射；
11. 输出必须补采或人工确认的问题；
12. 选择少量样本运行试导入；
13. 对账无误后才运行全量导入；
14. 全量导入后生成数量和质量对账报告；
15. 固定首个端到端演示案例。

首日禁止：

- 直接将 XLSX 转成正式业务表；
- 用文件行号作为长期稳定业务 ID；
- 将缺失来源的记录标成已验证；
- 把 L1–L4 与 T1–T7 合为一列；
- 把生成岗位或标准 JD 当作招聘数据；
- 为追求导入成功率而静默丢弃错误行。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| XLSX字段与预期不一致 | 延迟导入和算法开发 | 首日先画像和映射，DDL只做兼容性调整 |
| JD缺少时间或来源 | 无法可靠分析趋势 | 分级使用，缺时间数据不进入严格时间回测 |
| 里程碑来源不可验证 | 成熟度虚高 | 进入候选审核，不参加正式评分 |
| 技术双轴混乱 | 图谱和匹配语义错误 | 建立独立层级表、领域表和关系表 |
| 数据规模不足 | 新岗位证据不稳定 | 区分 potential/budding，不强行输出 emerging |
| 聚类不稳定 | 岗位版本频繁漂移 | 保存Top-K和谱系，用稳定岗位实体吸收变化 |
| LLM幻觉或注入 | 无依据结论 | 证据ID、Schema校验、Prompt隔离和专项评测 |
| 前端过早消耗时间 | 后端闭环延期 | Mock页面冻结，按纵向闭环逐页接API |
| 依赖安装或部署不稳定 | 演示失败 | 版本锁定、镜像缓存、离线演示种子和降级方案 |
| 时间不足 | 交付范围失控 | 优先P0纵向闭环，P1/P2功能不阻断核心验收 |

## 11. 正式开工判定

收到 XLSX 并完成阶段 0 的数据准入后，同时满足以下条件即进入正式开发：

- 原始文件已安全保存并有哈希；
- 字段画像和映射表已形成；
- P0缺失字段已有补采、推导或降级策略；
- 目标 DDL 调整已评审；
- 首批真实样本已固定；
- 开发环境可以建立；
- main 复用资产按本说明选择，不进行整分支合并。

满足后从“工程脚手架、技术主数据导入、证据底座”三项并行启动，第一目标不是一次性完成所有页面，而是在最短时间内跑通第一条真实、可追溯、可审核的纵向闭环。
