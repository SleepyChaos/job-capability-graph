# main 分支代码复用说明

> 文档版本：v1.0
>
> 审计基线：`main@fb416b1`
>
> 重构分支：`codex/redesign-from-scratch`
>
> 编写日期：2026-08-10
>
> 文档定位：指导重构开发期间从 main 分支选择性迁移算法、测试和工程经验，避免旧实现反向限制新架构。

## 1. 结论

main 分支不是新系统的实现基线，但包含若干经过原型验证的算法内核、降级策略、证据约束和测试资产。正确的复用方式是“抽取纯逻辑、重新接入目标领域模型”，而不是合并 main、复制旧数据库或恢复旧前端。

综合判断：

- 可直接抽取或轻量修改的代码约占 10%–15%；
- 需要重构数据访问和领域边界后复用的代码约占 15%–20%；
- 可保留的领域思路和接口契约约占 60%；
- 旧 SQLite 数据模型、FastAPI 单文件 API、旧前端信息架构和手写图谱页面不作为复用对象。

main 中最有价值的资产依次是：

1. 技术演化驱动的新岗位发现原型；
2. 确定性技术词抽取规则；
3. 人岗匹配基础数学函数；
4. IDF 加权岗位聚类基线；
5. 证据与置信度驱动的审核原则；
6. 101 个 Python 测试及其最小种子数据。

## 2. 复用原则

### 2.1 目标设计优先

任何旧代码只有在不破坏以下目标设计时才允许迁移：

- MySQL 8 是关系事实源；
- 原始数据、候选事实、已验证事实、正式领域数据和派生结果分层保存；
- L1–L4 技术层级与 T1–T7 技术领域是两个独立维度；
- 聚类版本与稳定岗位实体分离；
- 新岗位成熟阶段与审核工作流状态分离；
- 所有派生结果绑定输入数据版本、算法版本和证据；
- LLM 负责受约束抽取与表达优化，不能直接发布事实；
- 新岗位定义和生成标准 JD 永远不能反向计作真实市场证据。

### 2.2 只迁移内核，不迁移存储假设

优先迁移满足下列条件的代码：

- 输入和输出可以明确描述；
- 不依赖 SQLite 表名和全局连接；
- 不直接执行删除、覆盖或发布；
- 可以使用固定样本重复测试；
- 计算过程可解释且可保存分项结果。

原代码一旦同时承担“计算、读库、写库、审核状态变更”，应拆成领域函数、仓储接口和应用服务后再使用。

### 2.3 旧结果只作为基线

旧聚类、旧匹配分和旧新岗位候选只能用作算法对照或迁移验证，不能直接作为新系统的正式结论。迁移后必须重新绑定：

- 数据快照；
- 技术体系版本；
- 岗位版本；
- 算法配置版本；
- 证据 ID；
- 生成时间和目标时间截点。

## 3. 复用分级

| 级别 | 含义 | 处理方式 |
| --- | --- | --- |
| A：直接抽取 | 纯函数或稳定测试，不含旧存储语义 | 迁入新模块，补类型、边界和测试 |
| B：改造复用 | 核心算法有价值，但耦合 SQLite、旧表或旧状态 | 保留计算思想，重写仓储与持久化 |
| C：仅保留思路 | 方向合理，但实现不符合当前业务语义 | 依据当前设计重新实现 |
| D：不复用 | 会造成数据混淆、安全问题或架构倒退 | 不迁移，仅留审计记录 |

## 5. 分模块复用说明

### 5.1 技术词抽取

可保留能力：

- 中英文归一化；
- ASCII 技术词边界；
- 长词优先；
- 组合词拆分；
- 指标词的专用规则思想；
- 子词回溯；
- 每个命中附带证据窗口；
- 确定性词典命中使用较高初始置信度。

迁移时必须修改：

1. 证据必须指向原始文档版本和原文字符偏移，不能只保存归一化文本；
2. 同时使用标准词、正式别名和识别规则；
3. 技术词体系版本必须作为抽取运行输入；
4. 词典升级后允许只重跑受影响的文档，不能因文档已有任意边而整条跳过；
5. LLM 补充词先进入候选事实和标准化结果，不直接形成正式关系；
6. 禁止 `INSERT OR REPLACE` 覆盖人工审核过的关系；
7. 所有命中区分来源、提取方式、置信度、验证状态和证据。

建议目标模块：

```text
backend/modules/extraction/domain/term_matcher.py
backend/modules/extraction/application/extract_technology_terms.py
backend/modules/taxonomy/application/map_technology_term.py
```

主要目标表：`biz_extraction_run`、`biz_evidence_span`、`biz_extracted_fact`、`biz_technology_mapping_run`、`biz_technology_mapping_result`。

### 5.2 岗位导入与清洗

可以复用 Excel/CSV 列别名识别和基础工资解析，但必须放在“来源适配器”层。正式导入流程应为：

```text
原始文件资产
→ 文件哈希与来源登记
→ 表结构探查
→ 字段映射草稿
→ 原始行保留
→ JD 事实抽取
→ 精确去重和近重复检测
→ 质量评分
→ 发布或审核
```

旧版 `title + company + collect_time` 去重键不能沿用为唯一规则。它会在时间缺失时错误合并，也无法处理同一招聘页面的内容更新。新版本应综合来源 URL、外部 ID、正文哈希、企业、标题、地点和发布时间。

### 5.3 岗位聚类

旧 IDF 聚类作为 `baseline_keyword_idf_v1` 保留，使用场景：

- 算法单元测试；
- 关键词聚类基线；
- 向量模型不可用时的降级；
- 消融实验；
- 小规模数据的快速初分组。

禁止迁移以下行为：

- 模块级全局特征变量；
- 根据输入顺序产生不可复现的正式结果；
- 每次运行删除全部聚类；
- 重用 `C1/C2` 等不稳定 ID；
- 把聚类 ID 当成正式岗位 ID；
- 让 pending 技术关系参加正式聚类；
- LLM 直接生成非标准化共享技能。

正式方案必须保存聚类运行、参数、输入快照、Top-K 分配分数、灰区、版本和跨期谱系，并通过 `rel_job_cluster_role` 映射稳定岗位。

### 5.4 新岗位发现

旧版是最重要的复用来源。应保留：

- 技术实体链接；
- 里程碑贡献和时间衰减；
- 能力/任务模板与证据任务混合；
- 任务缺口的乘法门禁；
- 跨企业支撑；
- 分项评分；
- 证据路径；
- 规则、Mock、LLM 三种 Provider；
- 运行成功或失败均留痕；
- 候选提交后进入人工审核。

必须按《新岗位发现算法设计 v1》升级：

| 旧实现 | 新实现 |
| --- | --- |
| 目标日期只过滤里程碑 | JD、里程碑、主数据和岗位版本全部按 target_date 截止 |
| 非空关键词即认为 LLM 任务有证据 | 校验每个 evidence_id 和原文片段，关键词必须真实出现或有语义证据 |
| JD提及次数同时充当覆盖率 | 拆成市场支撑与已有岗位覆盖 |
| 固定任务组直接形成候选 | 构建任务图并执行社区发现，固定组只作先验或回退 |
| 只比较岗位名称 | 比较职责、能力、场景、级别和名称 |
| 七维正向加权 | 八维正向评分加重复、单企业、营销、冲突和幻觉惩罚 |
| 0.35成熟度下限参与最终判断 | 探索成熟度只用于召回，发布使用原始成熟度 |
| 总能从兜底模板产生候选 | 证据不足时输出观察项或 insufficient_evidence |
| 候选与审核状态混合 | 成熟阶段与审核状态独立 |
| 候选结果整体存 JSON | 运行、输入、任务、证据、候选、分数和最近岗位分别结构化保存 |

主要目标表：`biz_emerging_job_discovery_run`、`rel_discovery_run_input`、`biz_technology_maturity_snapshot`、`rel_maturity_milestone_contribution`、`biz_discovery_task`、`rel_discovery_task_evidence`、`biz_emerging_job_candidate`、`biz_emerging_candidate_score` 及相关关系表。

### 5.5 审核与幻觉防范

保留“来源类型、置信度、证据完整度共同决定发布路径”的原则。新审核机制必须区分：

- 数据审核：JD、技术词、里程碑、技术映射和聚类归属；
- 新岗位专项审批：岗位候选、机械事实卡、LLM 表达、岗位定义和标准 JD。

旧 `pending/approved/rejected` 三态不足。新审核任务至少支持：`pending`、`reviewing`、`needs_revision`、`approved`、`rejected`、`merged`，并保存领取人、修改前后快照、评论、风险原因和审计记录。

### 5.6 简历、画像和匹配

可以复用：

- PDF 文本提取适配器；
- 文本直接输入；
- 确定性技术词抽取；
- LLM 技能词映射本体后才进入正式能力集合；
- 无 LLM 时透明降级；
- 稀疏向量余弦、L1/T域分布和 Jaccard 基线。

需要重新实现：

- PDF、TXT、DOCX、图片和扫描件统一输入；
- 原文件、文本版本、画像版本三对象分离；
- 2–8 轮自适应追问；
- 工作经历、项目、教育、能力深度、性格倾向、发展方向和约束；
- 每个画像事实的来源、证据、置信度和用户确认；
- 岗位初筛、精排、逐要求差距和证据解释；
- 由差距驱动的发展路径与资源；
- 用户授权、脱敏、删除和审计。

旧匹配结果中的 `coverage = len(resume_skills) / 8` 不再使用“覆盖率”名称。新的岗位覆盖必须以岗位版本要求为分母，并按要求重要度、能力深度和证据可信度加权。

### 5.7 岗位演化

旧版快照差分的 `added/removed/modified` 表达可以保留，但不能继续使用“整份 JSON 快照 + 删除当前技能边”的实现。

新版本应：

- 由 JD 版本和分析周期形成岗位指标；
- 创建岗位版本草稿；
- 生成能力增删改建议；
- 保存每项变更证据；
- 审核通过后发布新岗位版本；
- 保留旧版本和有效期；
- 产生图谱投影刷新事件。

### 5.8 图谱与前端

旧前端不恢复。可以参考的内容只有：

- T1–T7 配色表；
- 图例、筛选、缩放、悬浮和节点详情等交互经验；
- 按领域设置布局锚点的实验参数；
- API 不可用时应显示明确错误态的意识，但不再静默替换为 mock 数据。

不复用 D3 Force + Canvas 手写渲染。新版本按既定设计引入成熟图谱渲染引擎，并将三类图谱拆成独立数据投影和页面：

1. 全局岗位—能力关联图；
2. 聚类岗位能力图；
3. 45 天能力热力网格。

热力图不能沿用旧版“L2 × 初中高职级”结构。

## 7. 明确不复用的内容

以下内容不得进入新系统主线：

- `db/schema.sql` 作为正式数据库结构；
- SQLite 连接层和运行时补列迁移；
- `backend/api.py` 的单文件路由组织方式；
- 通过 API 将 LLM Key 明文持久化到项目 `.env`；
- 客户端直接声明审核人；
- 无身份认证的简历、审核和设置接口；
- 覆盖式重聚类和覆盖式重提取；
- 将 pending 记录与正式事实混读；
- 将生成岗位定义或标准 JD 计入市场证据；
- 只按岗位名称判断新颖性；
- 只按技术词数量判断匹配差距；
- 前端接口失败时无提示地切换 mock；
- 手写 Canvas 图谱渲染页面；
- 旧页面导航和模块边界。

## 8. 测试资产迁移

main 共有 101 个 Python 测试。2026-08-10 在临时副本实测结果为 100 个通过、1 个因当前环境未安装 `pypdf` 失败。现有测试主要验证小规模种子数据下的功能链路，不代表真实数据质量或规模性能已经达标。

优先迁移：

1. 技术词归一化、边界、长短词和证据测试；
2. 成熟度过滤未来事件和时间衰减测试；
3. LLM 不可用时降级测试；
4. 无证据任务过滤测试；
5. 新岗位运行、提交和审核链路测试；
6. 稀疏向量、余弦和 Jaccard 测试；
7. 简历上传、技能提取、匹配和差距方向测试；
8. 审核门限和日志测试。

必须新增：

- 聚类质量、稳定性和谱系测试；
- target_date 防未来数据泄漏测试；
- 真实 evidence_id 校验测试；
- 45天热力逐日聚合测试；
- 高低可信事实分流测试；
- L1–L4 与 T1–T7 双轴测试；
- Prompt 注入与无依据陈述测试；
- 简历隐私、授权与删除测试；
- 100 条以上标注 JD/简历评测；
- 真实前端浏览器交互和响应式测试；
- 真实数据规模性能测试。

## 9. 实际迁移流程

每个被选中的 main 资产按以下流程处理：

1. 在本说明中确认复用等级；
2. 从 `main:<path>` 阅读原实现，不切换或合并 main；
3. 先迁移或重写相关测试；
4. 抽取不依赖数据库的纯函数；
5. 为纯函数定义领域输入输出类型；
6. 接入新仓储接口和目标表；
7. 增加数据版本、算法版本、证据和审计字段；
8. 使用旧最小种子验证行为未退化；
9. 使用新 XLSX 和真实 JD 验证业务口径；
10. 记录旧实现与新实现的差异及实验结果。

禁止使用 `git merge main` 或将 main 整个目录复制进重构分支。

## 10. 迁移优先级

### P0：首个纵向闭环必须使用

- 技术词抽取规则与测试；
- 成熟度公式和证据贡献；
- 新岗位评分框架与 Provider 降级；
- 稀疏匹配纯函数；
- 审核门限原则；
- 关键 API 链路测试场景。

### P1：形成完整模块时使用

- IDF 聚类基线；
- 简历 PDF/TXT 解析适配器；
- added/removed/modified 演化表达；
- Docker 多阶段构建思路；
- 前端领域配色和部分交互经验。

### P2：评测和扩展阶段使用

- Mock Provider；
- 旧前端接口类型作为兼容参考；
- 工资和多格式表格导入的扩展规则；
- 旧算法输出作为消融和基线结果。

## 11. 完成标准

复用工作只有同时满足以下条件才算完成：

- 没有引入旧 SQLite 表依赖；
- 没有覆盖用户数据或人工审核结果；
- 计算输入包含数据版本和目标时间；
- 输出包含算法版本、分项结果和证据；
- 单元测试与集成测试通过；
- 能说明相较 main 修复了哪些业务语义问题；
- 能在新 XLSX 和真实 JD 上重复运行；
- 不让生成内容进入真实证据统计。
