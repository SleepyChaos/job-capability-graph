# 数据库设计与数据包复用方案

> 文档版本：v1.0
>
> 数据批次：具身智能平台_数据库与数据包_20260810
>
> 目标结构：`database/target_schema_v1_mysql8.sql`
>
> 编写日期：2026-08-10

## 1. 文档目的

本文说明2026-08-10数据包如何进入当前重构项目，重点回答：

1. 数据包能覆盖哪些功能需求；
2. 目标数据库应如何承接这些数据；
3. 哪些文件可以导入，哪些只能重算或作为算法基线；
4. main分支的算法能力如何与新数据结合；
5. 还需要补充哪些数据；
6. 如何避免把个人数据、算法派生结果和生成内容误当成正式事实。

本文不采用数据包中曾经存在的旧SQL。项目数据库结构继续以当前分支的目标DDL为唯一基线，再根据真实XLSX字段做兼容性迁移。

## 2. 总体结论

这批数据足以启动正式开发，但不能独立覆盖全部功能闭环：

- 静态主数据覆盖约80%；
- P0开发所需初始输入覆盖约60%；
- 完整功能需求的数据覆盖约40%–45%。

已经具备的核心资产：

- 7个T技术领域、43个L2技术类、229个L3技术点和1872个L4表面词；
- 3718条清洗后的具身智能岗位JD；
- 18个岗位聚类基线；
- 10447条旧岗位关键词汇总和55127条旧岗位技术词命中；
- 1598家机构、196所高校、7815名产业人才及成果关系数据；
- 完整的技术标注和主数据维护规范。

仍然缺少或明显不足：

- 已验证技术里程碑；
- 连续45天以上的JD发布时间或每日采集历史；
- 原始网页/文件版本、采集请求和证据字符偏移；
- 稳定岗位实体、岗位版本和正式能力基线；
- 多模态简历、2–8轮追问和求职者画像；
- 人岗匹配与三项90%指标的人工金标准；
- 能力依赖、学习资源和发展路径数据。

因此实施策略是：用该数据包建立静态事实底座，用新系统运行逐步产生采集历史、审核记录、聚类版本、岗位演化、推演运行、画像和匹配结果。

## 4. 数据质量结论

### 4.1 技术词主数据

技术主数据具备较高完整度：

| 对象 | 数量 | 质量结论 |
| --- | ---: | --- |
| T领域/L1记录 | 7 | 编码T1–T7唯一 |
| L2技术类 | 43 | 编码唯一、父级完整 |
| L3技术点 | 229 | 编码唯一、父级完整 |
| L4技术词 | 1872 | 规范化后无重复，全部挂载L3/L2/T领域 |
| 跨域调整 | 153 | 全部保留调整说明 |

L4类型包括1491个细分词、154个组合词、152个指标词、53个型号词和22个碎片词。1872条均包含来源明细。

需要注意：文件将T1–T7直接作为“L1技术域”。目标数据库必须把“L1–L4层级”和“T1–T7领域”分别建模：

- `md_technology_node`保存技术层级；
- `md_technology_domain`保存T1–T7领域；
- `rel_technology_node_domain`保存主领域、多领域、权重、证据和版本。

首版可以按当前文件创建一一对应关系，但不能在数据库结构上把两个概念永久合并，否则无法表达跨域技术和聚类领域分布。

### 4.2 核心JD

3718条岗位均有唯一`occ_id`、唯一`group_id`、岗位名、清洗JD、标准学历、标准经验、能力等级和职业分类。

主要质量指标：

- 3391条唯一JD正文，存在327条完全重复JD；
- 3533条有链接，3518条为合法HTTP/HTTPS地址；
- 3条缺公司；
- 1732条缺城市；
- 2027条缺收录时间；
- 有时间的1691条只分布在2026-07-16和2026-07-17；
- 1946条缺旧技能标签；
- JD长度中位数402字，最长8799字。

导入时应保留`occ_id`、`group_id`和原始序号，但新系统仍需生成内部稳定ID。`occ_id`作为外部业务键，`group_id`作为来源去重/归并线索，不直接代替文档版本ID或稳定岗位ID。

### 4.3 机构、高校和人才

综合工作簿包含：

- 7815名人才，人才ID无重复；
- 1598家机构，机构ID无重复；
- 196所高校，高校ID无重复；
- 7603条人才—机构—成果关系；
- 7237条机构—标准关系；
- 7586条成果技术标注；
- 180条高校人才索引。

需要处理：

- 31条人才—机构—成果关系引用了机构库中不存在的机构ID；
- 独立高校文件与综合工作簿中的高校主表、人才索引完全一致，只导入一份；
- 582条机构官网中494条可直接识别为有效URL；
- 487条招聘链接中273条可直接识别为有效URL，其余需要拆分、清洗或人工确认；
- 人才库主要由专利发明人、标准起草人和高校科研人才构成，不等于求职者简历库。

人才姓名、任职和成果关系属于个人数据，必须实施访问控制、用途限制、导出审计和删除/匿名化策略，不得提交到公开代码仓库。

### 4.4 旧关键词派生数据

旧关键词文件包含10447个旧岗位ID、8066个命中岗位和55127条命中边，但与3718条核心JD的`occ_id/group_id`零交集。相同链接和JD在旧数据中普遍对应多个旧`job_id`，无法无歧义回填。

这些结果还存在以下限制：

- 没有证据片段和字符偏移；
- 只覆盖317个规范词、132个L3和38个L2；
- 输入使用另一批10447条旧岗位；
- 不能证明命中边经过当前技术词版本重新计算。

结论：不向正式岗位能力关系导入。保留为`legacy_keyword_baseline_v1`测试数据，核心3718条JD统一使用v1.1词表重新提取。

### 4.5 旧聚类数据

旧聚类文件将3718条核心JD全部分配到18个KMeans聚类，且序号、公司和岗位逐行对应，可以用作聚类基线。

不能作为正式聚类版本，原因包括：

- 缺少运行ID、算法参数和输入快照；
- 缺少成员相似度、Top-K候选和灰区；
- 缺少跨期谱系；
- 聚类代表岗位中存在销售、人力、资产定价等非技术岗位；
- 部分聚类名称被截断或混入多个维度；
- “能力缺口”仅按L2命中岗位数是否大于10判断，不能代表已有岗位覆盖缺口。

迁移时只作为`baseline_kmeans_l2_chain_level_v2`实验结果，不写入正式聚类和稳定岗位表。

## 5. 目标数据库设计

### 5.1 数据分层

| 层级 | 数据包落点 | 是否可直接参加正式算法 |
| --- | --- | --- |
| Source | 工作簿、来源标签、官网和招聘链接 | 否 |
| Raw | 原始XLSX文件、工作表、原始行和哈希 | 否 |
| Staging | 字段映射、清洗JD、候选技术关系 | 否 |
| Verified | 通过规则、交叉验证或人工确认的事实 | 是 |
| Domain | 正式JD、技术节点、能力、岗位和版本 | 是 |
| Derived | 聚类、周期指标、推演、匹配和学习路径 | 是，但必须绑定输入版本 |

### 5.2 技术体系

技术数据至少映射到：

- `md_technology_taxonomy_version`；
- `md_technology_node`；
- `md_technology_alias`；
- `md_technology_domain`；
- `rel_technology_node_domain`；
- `biz_technology_term_candidate`；
- `biz_technology_mapping_run`；
- `biz_technology_mapping_result`。

L3作为图谱默认标准技术点，L4作为文本识别表面词。能力匹配仍以`md_capability`为主要单位，通过`rel_capability_technology`映射技术点，避免把团队协作、系统设计和现场调试等非技术能力强行塞进技术树。

### 5.3 JD和证据

工作簿本身登记为`raw_file_asset`，每次导入建立`biz_extraction_run`。每一行先生成可追溯的原始记录，再发布到：

- `biz_job_posting`；
- `biz_job_responsibility`；
- `biz_job_requirement`；
- `rel_job_scenario`；
- `biz_evidence_span`；
- `rel_job_fact_evidence`。

由于交付的是清洗JD而非原始网页快照，迁移记录必须标记为`migrated_cleaned_source`。证据可以暂时定位到“工作簿+工作表+原始行+JD字段”，后续重新采集成功后再关联网页文档版本。

### 5.4 聚类和岗位版本

正式聚类不得复用旧C00–C17作为稳定业务ID。新系统每次运行写入：

- `biz_job_clustering_run`；
- `biz_job_cluster_version`；
- `rel_job_cluster_member`；
- `rel_job_cluster_lineage`；
- `rel_job_cluster_domain`。

聚类通过`rel_job_cluster_role`映射`biz_job_role`。稳定岗位的职责、要求、能力和场景写入`biz_job_role_version`及其关系表。聚类可以拆分、合并和结束，稳定岗位ID保持不变。

### 5.5 新岗位发现

数据包当前能提供技术词、JD、企业、场景和旧聚类基线，但不能提供合格的里程碑和时间序列。新岗位发现继续使用：

- `biz_emerging_job_discovery_run`；
- `rel_discovery_run_input`；
- `biz_technology_maturity_snapshot`；
- `biz_discovery_task`及证据关系；
- `biz_emerging_job_candidate`；
- `biz_emerging_candidate_score`；
- 候选职责、能力、领域、最近岗位和证据关系；
- `biz_generated_job_description`及版本。

生成岗位卡和标准JD均标为生成内容，不能反向计入真实JD支撑数。

### 5.6 人才与求职者画像

产业人才库与求职者画像是两个不同对象：

- 产业人才、机构和成果进入主数据/研究扩展模块；
- 用户上传简历进入`biz_resume`；
- 求职者进入`biz_candidate_profile`和版本；
- 追问进入`biz_profile_conversation`和消息；
- 匹配进入`biz_match_run`、结果、维度和逐要求差距；
- 学习路径进入`biz_learning_path`和步骤。

不得用产业人才的技术标签代替简历解析、用户确认和画像版本。

## 6. 文件级复用方法

### 6.1 可转换导入的核心文件

#### 技术词主数据

导入顺序：

```text
登记文件与哈希
→ 建立技术体系版本
→ 导入T领域
→ 导入L1/L2/L3层级节点
→ 导入L4表面词与别名
→ 建立技术—领域关系
→ 校验编码唯一性和父子完整性
→ 发布版本
```

#### 核心JD

导入顺序：

```text
登记文件和工作表
→ 保存原始行
→ 外部ID与字段映射
→ 精确去重和近重复检测
→ JD结构抽取
→ 证据绑定
→ 技术词重新提取
→ 高低可信分流
→ 正式JD发布
```

#### 机构、高校、人才和成果

先导入机构和高校，再导入人才与成果关系。所有外键悬挂记录进入导入错误表，不静默丢弃，也不自动创建没有名称和来源的空机构。

### 6.2 只作为基线的数据

| 文件 | 基线用途 | 禁止用途 |
| --- | --- | --- |
| 旧关键词命中 | 技术词抽取回归、召回率对比 | 正式岗位能力边 |
| 旧关键词汇总 | 旧数据对账、来源去重研究 | 核心JD主表 |
| 旧KMeans聚类 | 聚类消融、稳定性对比 | 正式聚类版本和岗位实体 |
| 旧能力缺口地图 | 页面样例和算法反例 | 新岗位缺口结论 |

### 6.3 main分支代码复用

按照《main分支代码复用说明》执行：

- 抽取技术词正则规则和测试，不迁移SQLite写库逻辑；
- 抽取成熟度、稀疏向量、余弦和Jaccard等纯函数；
- 将IDF聚类保留为基线；
- 将旧新岗位七维评分升级为当前八维评分、惩罚项和硬门槛；
- 将Rule/Mock/LLM Provider接入统一LLM网关；
- 将旧测试迁移为新数据模型的遗留回归测试；
- 不合并main，不恢复旧前端，不采用旧SQLite结构。

## 8. 必须补采和构建的数据

### P0

1. 技术里程碑：事件、日期、类型、主体、技术关系、来源URL、原文和验证状态；
2. 时间序列JD：岗位发布时间或至少连续45天采集历史；
3. 正式岗位能力基线：职责、要求、能力、场景、级别和证据；
4. 100–300条人工标注JD；
5. 脱敏简历、技能标注和人岗匹配样本。

### P1

- 非技术能力和能力深度；
- 技术/能力前置依赖和可迁移关系；
- 学习资源；
- 更多企业官网、招聘页和政府/协会来源；
- 新岗位候选专家评审集。

## 9. 导入验收规则

每个工作簿必须满足：

- 保存原文件路径、文件名、大小和SHA-256；
- 保存工作表、原始行号和外部ID；
- 重复执行保持幂等；
- 原始值和标准值分开；
- 错误行可定位、修正和重放；
- 不静默删除外键悬挂和冲突记录；
- 所有派生结果保存算法版本和运行ID；
- LLM生成内容保存模型、Prompt、输入证据和Schema校验结果；
- 未审核候选不能进入正式事实查询；
- 生成岗位和标准JD不能计入真实市场证据。

## 10. 隐私与仓库策略

当前GitHub远程仓库为公开仓库。以下文件包含个人姓名、职务、任职和成果关系，默认不得提交到公开远程：

- `科技人才库与机构库_20260731.xlsx`；
- `高校库_20260727.xlsx`中的高校人才明细索引。

安全方案原则上二选一：

1. 公开仓库仅提交非个人数据工作簿，个人数据保存在受控本地/私有对象存储，并提交字段说明和哈希；
2. 将仓库改为私有，确认访问成员和使用目的后再提交完整数据包。

即使仓库为私有，后端仍需落实授权、最小权限、日志脱敏、导出审计和删除/匿名化机制。

本数据批次根据项目负责人2026-08-10的明确指令全量提交到当前公开仓库。此操作属于本批次的显式例外，不改变生产系统的隐私设计和后续数据治理要求。

## 11. 推荐启动顺序

1. 提交数据说明、非敏感XLSX和哈希；
2. 建立MySQL迁移和Raw文件登记；
3. 导入技术体系双轴主数据；
4. 导入3718条JD到Raw/Staging；
5. 重跑技术词抽取并建立证据；
6. 导入机构和来源候选；
7. 建立聚类基线与正式版本化聚类；
8. 补充里程碑并开发新岗位发现；
9. 从采集运行积累45天热力数据；
10. 准备脱敏简历和人工标注集，开发人岗闭环。
