# 系统架构与数据流

## 技术结构

```text
React 19 + TypeScript + AntV G6
              │ /api
              ▼
FastAPI + SQLAlchemy 2 + Pydantic
              │
              ▼
MySQL 8 + Alembic ── 运行快照 / 核心 XLSX
              │
              ├── DeepSeek OpenAI-compatible API（可选）
              └── 本地文件存储（生产待替换）
```

- 前端：Vite 单页应用，Hash 路由；业务请求集中在 `frontend/src/api`。
- 图谱：AntV G6 5 Canvas 渲染；大图由 Web Worker 执行 D3 Force 布局。
- 后端：按 taxonomy、job、ingestion、clustering、discovery、graph、talent 分模块。
- 数据库：项目自身 13 个 Alembic 迁移是唯一结构来源，不使用外部数据包中的废弃 SQL。
- 交付：Docker Compose 编排 MySQL、恢复、迁移、补全、后端和前端；GitHub Actions 执行后端检查与前端构建。

## 主数据链路

```text
核心 XLSX
  → 文件画像与准入
  → 不可变 Raw 行账本
  → 技术体系 / JD 发布
  → JD 结构化切分
  → 技术词初筛 + 上下文复核
  → 可选 DeepSeek 闭集复核
  → 聚类特征快照
  → 岗位聚类与灰区
  → 岗位版本人工审批
  → 图谱 / 新岗位发现 / 人岗匹配
```

数据导入以文件、映射、结构和输入快照指纹保证幂等。解析与聚类运行冻结版本和参数，同样输入不应生成不受控的新结果。

## 三条业务闭环

### 岗位—能力闭环

真实 JD 证据关联到标准技术节点；岗位聚类汇总成员 JD 的技术覆盖率与重要度；只有已审批岗位版本进入正式岗位口径。图谱是这些关系的投影，不另造事实。

### 新岗位发现闭环

确定性算法形成候选和评分，LLM 只改善名称、定义或解释。专项审批通过后才创建 `inference_derived` 岗位；其标准 JD 永久标记为非市场证据，不能反向抬高市场热度。

### 人岗匹配闭环

简历生成可追溯候选人画像，岗位侧使用已审批版本。多维分数由固定规则计算，LLM 只组织解释，不得改变分数。缺少个人证据表示“未证明”，不等同于“不会”。

## 核心接口域

| 接口域 | 用途 |
| --- | --- |
| `/taxonomy/*` | 技术版本、领域和节点 |
| `/jobs/*`、`/job-parsing/*` | JD 查询、解析运行和证据 |
| `/sources/*`、`/collection-*`、`/reviews/data/*` | 来源、采集、里程碑和数据审核 |
| `/job-clustering/*`、`/job-clusters/*`、`/job-roles/*` | 聚类、岗位和岗位审核 |
| `/role-discovery/*` | 三种新岗位推演和专项审批 |
| `/graphs/*` | 关系图、邻居、单簇图和热力图 |
| `/talent/*` | 简历、画像、匹配和发展路径 |

完整参数和返回结构以启动后的 `/docs` OpenAPI 为准，避免在 Markdown 中复制 59 个路由定义。

## 必须保持的数据约束

1. LLM 不能创建技术编码、修改机械评分或用无法逐字定位的引文作为证据。
2. 算法簇不是正式岗位；岗位发布必须经过审核。
3. 推演生成的标准 JD 不是市场 JD。
4. 数据包只提供源数据，数据库结构只由本项目迁移维护。
5. 任何批处理必须记录输入快照、算法/Prompt 版本、参数和运行状态。
6. 影响正式投影的操作必须可审计、可重放，并保留发布前后状态。
