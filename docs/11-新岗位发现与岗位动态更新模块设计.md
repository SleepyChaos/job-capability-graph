## 1. 问题与设计目标

具身智能是一个技术路线尚未收敛的领域，岗位名称高度不稳定：同一份工作可以叫
"具身智能算法工程师""VLA 模型算法工程师""机器人大模型研究员"。直接按岗位名称统计，
得到的是招聘文案的措辞分布，不是能力结构的分布。

因此两个模块共用一个设计前提：**岗位由能力集合定义，不由名称定义。**

| 模块 | 要回答的问题 | 输出 |
| --- | --- | --- |
| **岗位动态更新** | 同一个岗位在两个时间点上的能力要求变了吗？变在哪里？ | 岗位版本 + 演化事件 + 逐项变更 |
| **新岗位发现** | 语料里是否出现了既有岗位无法覆盖的能力组合？ | 岗位候选 + 成熟度分档 + 机械事实卡 |

两者共享同一条证据链路：JD → 技术要求 → 特征 → 簇 → 岗位版本。**新岗位发现的输入是
岗位动态更新的输出**——只有先有稳定的"既有岗位"定义，"新"才有参照系。

## 3. 输入侧：证据的产生与治理

### 3.1 技术词表：四层结构与版本化治理

词表是整条链路的坐标系。四层结构：

| 层 | 含义 | v1.1 | v1.2 |
| --- | --- | ---: | ---: |
| L1 技术域 | T1–T7（算法/传感/整机/数据/系统/安全评测/场景） | 7 | 7 |
| L2 技术类 | 如 T1.03 运动规划与控制 | 43 | 43 |
| L3 技术点 | **能力图谱的基本单元**，如 T1.03.02 模型预测控制 | 229 | **242** |
| L4 表面词 | 招聘语料里的实际写法，如 `MPC`、`模型预测控制` | 1,872 | **2,073** |

**升版不改数据库，而是"基线工作簿 + 变更集 → 新工作簿 → 暂存 → 导入"。** 变更集是仓库内的
JSON，整条链路只依赖仓库文件，任何人重跑得到逐字节相同的工作簿。这样做的原因是每个技术节点
都必须能回溯到某一行电子表格（`source_spreadsheet_row_id` 非空），直接改库会切断这条溯源链。

变更集只有三种原语：

- `retire_terms` — 把既有表面词的「可匹配」置否。**保留行与谱系，只是不再参与匹配**，
  历史运行仍可解释。
- `new_l3` — 新增技术点
- `new_terms` — 新增表面词

「收窄一个过宽词」不是独立原语，它等于「下线宽词 + 新增若干窄词形」。这样每条改动都能在
工作簿里逐行看到，不需要另一套规则表。渲染器会挡住三类错误：新增词与既有词重复、挂载的
上级不存在、**同一词形跨节点重复**（后者会让命中归属依赖别名 id 顺序，破坏可重放性）。

> 复现：`python backend/tools/build_taxonomy_workbook.py --base <v1.1.xlsx> --changeset data/governance/taxonomy_v1_2_changeset.json --out <v1.2.xlsx>`

**跨版本并存。** `biz_job_requirement` 带 `taxonomy_version_id`，同一份 JD 可同时持有 v1.1 与
v1.2 两套抽取结果；历史解析运行通过自己的词表版本读回原始口径，不被新版覆盖。

### 3.2 技术词抽取与歧义消解

抽取是确定性的 Aho-Corasick 多模式匹配，最长优先消解重叠，要求 ASCII 词边界
（避免 `ros` 命中 `roscpp` 之类的子串误配）。命中即产生一条 `biz_job_requirement`
和逐字可定位的证据跨度（`start_offset`/`end_offset`/`evidence_hash`）。

少数词天然歧义（"控制系统"既可能指机器人运动控制，也可能指工业 SCADA）。这些词走**歧义规则**：

```
语境权重 = Σ (同句出现的正向语境词权重)
≥ 1.0 → accepted（置信 80，特征权重 0.85）
< 1.0 → needs_review（置信 35，特征权重 0.35）
```

两处关键设计：

1. **语境窗口是"命中词所在句"，不是整段。** v1 用整段共现，结果"机器人"这一个泛词
   在语料里放行了大量销售/产品岗——同段出现不构成句法关联。
2. **语境词带权重，泛触发词降权。** "机器人"权重 0.5（需与另一个词共现），
   "伺服""运动控制""关节"权重 1.0（单独即可放行）。权重依据是各词的实测触发频次
   与 LLM 复核接受率。

v1.2 下歧义规则只保留 3 条（控制系统、多模态大模型、基础模型）。原先的"检测""汽车""大模型"
三条已随词形下线而退场——实测这三个词的语境放行路径几乎全是误报（"大模型"的 LLM 复核
接受率仅 1/233）。**需人工复核的命中从 735 条降到 126 条。**

### 3.3 双重门控：两道门管两件事

两道门经常被混为一谈，实际口径完全不同，**不可互相替代**：

| | 低信息量门 | 职能门 |
| --- | --- | --- |
| 判据 | 特征快照里技术点条数 | 岗位名称的职能词 |
| 管的是 | **聚类形态**（碎片化） | **非具身智能技术岗** |
| 生效位置 | 聚类入口 | 特征快照（更早） |
| 默认值 | ≥ 1 | 4 类职能词表 |

**低信息量门的标定。** 用 `tools/calibrate_domain_gate.py` 在内存里跑聚类算法本身
（不落库），对一组门槛逐一测量结果形态。词表 v1.2 下的实测：

| 门槛 | 参与聚类 | 簇数 | 单例簇 | 单例JD比 | p90 | 一致性 | 灰区比 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 3,534 | 2,211 | 1,728 | 48.9% | 2 | 64.23 | 24.5% |
| **1** | 1,671 | 616 | 337 | **20.2%** | **5** | 83.62 | 33.8% |
| 2 | 1,132 | 557 | 330 | 29.1% | 4 | 85.74 | 45.2% |
| 3 | 788 | 434 | 267 | 33.9% | 3 | 86.66 | 49.9% |

门槛 1 是拐点。再往上一致性还在涨，但**单例比反而回升、灰区激增**——那是幸存者偏差
（剩下的都是高证据 JD，自然更像），不是质量改善。

**职能门的由来是一个否定结果。** 原计划用低信息量门过滤非技术岗，实测证明这条路走不通：

| 门 | Precision | Recall | F1 |
| --- | ---: | ---: | ---: |
| 无门（v1.2 原样） | 0.585 | 0.444 | 0.505 |
| 证据数门槛 2 | 0.618 | 0.423 | 0.502 |
| **职能标题门** | **0.693** | **0.444** | **0.541** |
| 理想门（标注 role_type 作 oracle） | 0.705 | 0.444 | 0.545 |

原因是：零证据的非技术岗**本来就不产生误报**，过滤它们对证据质量毫无改变；而真正产生误报的
非技术岗（销售/产品/采购）与低证据技术岗在条数上完全重叠，抬高门槛只能等比例牺牲召回，
F1 从门槛 2 起单调下降。

改用**岗位名称的职能词**后几乎打满理想上限，且零召回损失（TP 与 FN 完全不变）。
招聘语料的岗位名高度模式化，职能类别在名称里几乎总是显式出现。四类规则：

| 类别 | 例词 | 全语料命中 |
| --- | --- | ---: |
| commercial 商务 | 销售、客户经理、业务拓展、采购、渠道 | 314 |
| product_ops 产品与职能管理 | 产品经理、项目经理、运营经理、人力、财务 | 286 |
| manufacturing 制造工艺与质量 | 电镀、焊接、抛光、SMT、模具、SQE、质量工程师 | 187 |
| it_ops IT 运维与安全 | 运维工程师、网络安全 | 11 |

（表中为「职能门是唯一排除原因」的计数，合计 798；另有 50 份同时触发了其它排除原因。）

判的是「**非具身智能技术岗**」而非「非技术岗」——电镀/抛光/SMT 有自己的技术性，
但不属于具身智能能力图谱的测量对象。纯机械子串匹配，确定性、逐条可解释，不引入 LLM。

被判出的 JD **抽取结果与证据完整保留**，只是不纳入聚类与岗位画像聚合，理由逐条写进
`exclusion_reason_json`——是「不纳入统计」，不是「删数据」。

实测：3,718 份 JD 中 848 份命中职能规则（22.8%）——其中 50 份本来就会因「无结构化聚类信号」或「解析质量过低」被排除，**职能门的净效果是 798 份**，可聚类特征从 3,534 降到 **2,736**。

### 3.4 抽取质量的测量方法

**分层抽样标注对照。** 100 份 JD 按 T1–T7 分层抽样，人工标注 `expected_l3_codes`
（该 JD 应当抽出哪些技术点），与实际抽取结果做集合比较，指标为 micro P/R/F1，
置信区间用 JD 级 bootstrap 重采样（B=2000，种子固定）。

**跨版本对比必须用受限口径。** 标注是在 v1.1 的 229 个代码空间里写的，v1.2 新增的 13 个
技术点在真值侧永远缺席——直接对照会把新技术点的每一次正确命中都算成误报
（naive 全口径给出 P 0.451，看起来精确率下降了，实际上那些"误报"多数是标注空间缺失）。
受限口径把预测与真值都交到 v1.1 的 229 个代码上，两版在完全相同的判定空间里比较。

| 分层 | v1.1 | **v1.2** |
| --- | ---: | ---: |
| 总体 Precision | 0.511 [0.410, 0.611] | **0.585** [0.491, 0.680] |
| 总体 Recall | 0.341 [0.283, 0.399] | **0.444** [0.382, 0.505] |
| **总体 F1** | **0.409** [0.343, 0.468] | **0.505** [0.440, 0.562] |
| 具身算法岗 (25) | 0.471 | 0.545 |
| 硬件岗 (12) | 0.507 | 0.571 |
| 工程岗 (23) | 0.394 | 0.531 |

逐项改动的贡献可以拆开：

| 改动类别 | 新增 TP | 新增 FP | 减少 TP | 减少 FP |
| --- | ---: | ---: | ---: | ---: |
| 新增表面词 | **31** | 17 | 0 | 0 |
| 下线过宽词 | 0 | 0 | 2 | **19** |
| 歧义规则 v2 | 0 | 0 | 0 | 1 |

召回提升几乎全部来自新增表面词，精确率提升几乎全部来自下线过宽词——两类改动各自解决
一个问题，互不重叠。

**⚠️ 标注局限（必须随结论声明）**：单人标注、标注者非领域专家、未经双人独立标注与仲裁。
这组数字**仅作版本对比的参考基线，不构成性能声明**。

> 复现：`python backend/tools/evaluate_extraction_quality.py --package docs/reports/annotation_package/jd_annotation_batch_001.annotator_C.v1_2.json --restrict-codes docs/reports/annotation_package/v1_1_l3_codes.json`

## 4. 岗位动态更新模块

### 4.1 岗位的定义：从 JD 聚类到岗位版本

**JD 聚类**把能力结构相近的 JD 归到一起，簇即"一个岗位"的证据集合。相似度是六通道加权余弦：

| 通道 | 权重 | 内容 |
| --- | ---: | --- |
| responsibility 职责 | 0.326 | 职责句的动词-宾语词元 |
| capability 能力 | 0.272 | L3 技术点及其重要度权重 |
| title 名称 | 0.217 | 岗位名称词元（去除城市/编号等噪声） |
| domain 技术域 | 0.109 | T1–T7 域分布 |
| level 层级 | 0.076 | 按序数距离：同级 1.0、相邻 0.5、跨两级 0.0 |

职责权重高于名称，正是因为名称不稳定而职责稳定——这是"岗位由能力定义"这一前提的具体落实。

原设计还有一个 `scenario` 通道占 0.08，但场景特征从未被填充、恒为 0，
相似度的**有效满分只有 0.92**，`assign_threshold=0.36` 实际卡在 0.391 的位置上。
现已把空通道摘掉、权重按原比例归一化到剩余五通道，满分回到 1.0；默认阈值同步
按 1/0.92 上调到 0.391/0.261 以保持行为等价，使后续改动的效果不会与这次口径修正混淆。

层级相似度原本是二值的（相同得 1、否则 0），于是"初级 vs 中级"与"初级 vs 高级"
同样得 0，丢掉了层级的序关系；语料里 senior 与 middle 各占约一半，这个区别不小。

**算法分两阶段。** 先是**单遍贪心 leader 聚类**：JD 按名称+编码确定性排序后逐个进入，
用倒排块索引取候选簇，算相似度，超过 `assign_threshold` 则加入，介于 `grey_threshold`
与它之间落入灰区待治理，都不满足则自立新簇。

单遍贪心的成员集合会受 JD 进入顺序影响——先进的成员把质心拉偏后，后来更相似的 JD
反而进不来。因此其后追加**Lloyd 式迭代重分配**：重算质心 → 全局重分配 → 直到稳定。
两处与教科书 k-means 的差别都是被约束逼出来的：

1. **批量应用而非边算边移**——先用同一批质心算完所有 JD 的目标簇再统一应用。
   边算边移会让结果依赖处理顺序，那正是要解决的问题。
2. **`max_cluster_size` 是硬约束，会破坏 Lloyd 的单调收敛**——目标簇满员时按相似度
   降序接纳，落选的留在原簇。因此必须设最大轮次，并检测"划分回到此前状态"的振荡。

够不上阈值的 JD 留在原处，不强行分配——它可能是自成一簇的合理离群点。
逐轮移动数、簇数、清空簇数写入 `quality_metric_json.reassignment`，收敛过程可复核。

**簇 → 岗位晋升**：满足规模与一致性门槛的簇被提为岗位候选，经评审后成为 `biz_job_role`
及其首个 `biz_job_role_version`。当前 374 个岗位、542 个岗位版本，全部为 `cluster_derived`。

### 4.2 簇谱系：岗位连续性的判定

这是动态更新的核心难点：**两次聚类运行产出的簇是两批全新的对象，怎么知道哪个是哪个的延续？**

设计是**按成员重合度匹配**：新簇与旧簇的成员 JD 集合 Jaccard ≥ 0.55 判定为同一岗位的延续。
五种谱系关系：

| 关系 | 判定 | 当前累计 |
| --- | --- | ---: |
| `continued` | 一对一匹配 | 6,818 |
| `born` | 新簇无匹配前身 | 4,807 |
| `ended` | 旧簇无匹配后继 | 1,893 |
| `split` | 一个旧簇匹配到多个新簇 | 92 |
| `merged` | 多个旧簇匹配到一个新簇 | 70 |

只有 `continued` 的簇才会产生**岗位新版本**；`born` 产生新岗位，`ended` 让岗位进入非活跃。
这样"岗位演化"就有了严格定义：同一 `job_role_id` 下相邻两个 `version_no` 之间的能力要求差异。

### 4.3 岗位版本与演化事件

每次聚类运行后，`continued` 的岗位重算能力画像并与上一版逐项比较，产出：

- `biz_job_evolution_event` — 事件层：`created` / `updated`（当前 374 / 168）
- `biz_job_evolution_change` — 变更项层：逐个技术点的新增、消失、重要度升降（当前 1,281 条）

每条变更都挂着支撑它的证据跨度，可以下钻到具体 JD 的具体句子。

### 4.4 特征表示：一个让最高权重通道空转的缺陷

职责通道权重最高（0.326），但它原先建立在一个错误的中文切词方式上。

中文没有空格分词，原实现取 `[一-鿿]{2,12}`——即**任意 12 字切片**。后果是两句几乎
同义的职责：

> 负责具身智能机器人**运动控制算法**的设计与实现
> 负责人形机器人**运动控制算法**开发与调优

切点不同，**token 交集为空**，尽管两句都含"运动控制算法"。实测 31,565 个职责 token 中
**74% 只出现在一份 JD 里**——这个通道一直在贡献噪声而非信号。

英文那侧是另一种失效：两句英文职责的交集是 `{and, for, control, robots}`，
一半是虚词。`and` 是职责通道第 11 高频的 token。

改为**中文字符二元组 + 英文停用词过滤**后，上面两句共享 9 个 token
（运动/控制/算法/机器/器人…）。二元组会引入噪声词，但 IDF 加权会把高频二元组压下去，
这是无分词器场景的标准做法。

### 4.5 三项改动的实测效果

在同一批 JD 上逐项做开关对照：

| | 簇数 | 单例簇 | 单例JD比 | 中位簇 | 灰区比 | 一致性 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| v2 基线 | 560 | 311 | 22.3% | 1 | 36.9% | 84.17 |
| + 相似度口径修正 | 515 | 282 | 20.2% | 1 | 34.1% | 91.22 |
| + 迭代重分配 | 515 | 282 | 20.2% | 1 | 34.1% | 91.22 |
| **+ 中文分词重建** | **361** | **169** | **12.1%** | **2** | **23.8%** | 86.87 |
| **+ 语种门** | **357** | **168** | **12.6%** | **2** | **24.5%** | 87.03 |

三条结论：

1. **碎片化的主因是特征表示，不是聚类算法。** 分词重建单独把单例簇从 282 降到 169
   （−40%）、灰区从 34.1% 降到 23.8%，是所有改动里最大的一笔。
2. **迭代重分配在这份语料上收益可忽略**——只移动 5 份 JD、1 轮收敛，簇数/单例/一致性
   均无变化（分词修好后移动数升到 28，仍不改变聚合指标）。这是个否定结果：
   小簇的质心本就几乎不漂移，Lloyd 无事可做。机制保留（默认开启、`0` 轮可关闭），
   它保证的是"结果不依赖 JD 进入顺序"这一性质，**不能据此宣称聚类质量提升**。
3. **一致性下降不是退步。** 91.22 → 87.03 伴随着单例簇腰斩——原先的高一致性有相当部分
   来自"簇里只有自己"这种退化情形。见 §4.6 的判据讨论。

### 4.6 阈值标定：为什么不能用一致性、也不能只信轮廓系数

`assign_threshold` 从未被数据标定过。扫描它会得到一条清晰的权衡曲线，但**判据的选择
比曲线本身更关键**：

**不能用一致性选阈值。** 一致性只看簇内相似度，阈值越高簇越碎、一致性越高，
极限是每份 JD 自成一簇、一致性 100——退化解。

改用**轮廓系数**（`s = (a-b)/max(a,b)`，`a` 为到自身质心的相似度，`b` 为到最近的其它簇
质心的相似度；单例簇按惯例记 0）。它同时惩罚碎片化与过度合并，确实有内部极值：

| 分配阈值 | 簇数 | 单例JD比 | max簇 | 一致性 | 轮廓系数 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.320 | 141 | 2.8% | 100 | 74.63 | 0.3226 |
| **0.360** | 244 | 7.1% | 78 | 82.38 | **0.3277** |
| 0.391（当前） | 357 | 12.6% | 60 | 87.03 | 0.3254 |
| 0.440 | 513 | 20.7% | 28 | 91.09 | 0.3094 |

**但轮廓系数的最优点经人工核对是过度合并的，不予采纳。** 在分词修复前的数据上，
轮廓系数最优的 0.31 处最大的簇装着：

> helix data creator / ai researcher / battery test engineer / biomechanics researcher /
> chief of staff / commercial launch technician / android开发工程师

这不是一个岗位。轮廓系数奖励"彼此分离的团块"，而一堆互不相似的 JD 因为离所有簇都远，
反而能拿到不差的分数。**几何判据不知道什么叫"一个岗位"。**

因此默认阈值维持 0.391，标定曲线与人工判读一并记录在案。这也是本模块的一条方法论立场：
聚类质量的最终判据是"簇能否作为岗位定义使用"，几何指标只用来缩小搜索范围。

### 4.7 语种门：一个由特征管线能力边界产生的假岗位

上面那个"杂物堆"簇在分词修复后仍然存在（65 份，其中 **62% 是英文 JD**——语料里 59 份
英文 JD 有 40 份落在里面，而同等规模的其它簇英文占比为 0）。

原因是整条特征管线面向中文语料：中文切二元组、英文只留实词。英文 JD 拿到的是稀疏向量，
只能与彼此匹配。**这个簇不是岗位，是"特征管线表示不了的 JD"的残余桶**，一旦被晋升为
岗位就是纯粹的假阳性。

处理方式与职能门一致：中文字符占比低于 10% 的 JD 标记 `unsupported_feature_language`，
抽取结果与证据完整保留，只是不纳入聚类与画像聚合。加门后最大簇变成
**嵌入式软件 / BSP 驱动开发**（60 份），是真实的岗位族。

**代价必须声明**：这部分岗位（59 份，占参与聚类 JD 的 4.2%）在能力图谱中没有覆盖。

### 4.8 一个被实测抓出来的谱系缺陷

谱系的前身查询原本按 `algorithm_version` 过滤，导致**每次算法升版，全部簇都找不到前身
而被判为 `born`，所有岗位被当成新岗位重建**。对一个以追踪岗位演化为目的的模块，
这等于每升一次版就丢掉全部历史。

实测证据：v2→v3 升版那次运行 515 个簇全部判为 `born`、0 个 `continued`；
下一次同版本运行则是 515 个 `continued`、成员重叠度 0.998——簇本身根本没变，
断裂纯粹是过滤条件造成的。

延续与否由成员集合的 Jaccard 判定，这个判据与算法内部无关，因此该过滤条件被去掉；
跨算法版本的谱系边在说明文字里标注，供下游区分"真实演化"与"换算法"。

该缺陷已经造成 89 个本应是延续的岗位被建成新岗位。**它们全部停在 `pending`，
没有一个进入已批准集合**——机械环节出错时，人工评审门按设计拦住了它。

### 4.9 仍然存在的局限

**观测窗有合成成分。** 3,718 份 JD 中约 2/3 的采集时间为初始化时统一赋值
（`time_quality_code='synthetic_window_spread'`），月粒度。这意味着**基于时间轴的
演化速率结论目前不可靠**，只有能力结构的差异是可靠的。

## 5. 新岗位发现模块

### 5.1 三种推演模式

| 模式 | 输入 | 用途 |
| --- | --- | --- |
| `automatic` | 无 | 从全语料自动挖掘未被覆盖的能力组合 |
| `technology_directed` | 指定技术点集合 | "如果 X+Y 技术成熟，会出现什么岗位" |
| `name_inference` | 岗位名称/描述 | 判断某个业界新名词是否已有证据支撑 |

三种模式共用同一套证据与评分，只在候选生成入口不同。

### 5.2 候选生成：频繁技术组合

候选是"一组共同出现的技术点"。原设计用 JD 内**任意两个技术的共现**（技术对），
这让核心测量失效——见 5.3。

现在用**频繁闭项集挖掘**：把每份 JD 的 L3 技术集合当作一条事务，逐层 Apriori 求支持度
≥ `min_pair_job_count`(2) 的项集，限制大小在 2–5，再做闭包过滤。

**为什么要闭包。** 频繁项集天然冗余：若 {A,B,C} 在 20 份 JD 中出现，它的全部子集也至少
出现 20 次，直接枚举会产出大量"同一批 JD 的不同切片"。闭项集（没有任何超集与之支持度相同）
只保留每个支持度等价类里最大的那个，去冗余且不丢支持度信息。

**排序不能只看支持度。** 项集支持度沿子集单调不减，纯按 JD 数排序会让候选名额几乎全被
最小组合占满（首次真跑 100 个候选里 82 个仍是二元组，粒度提升等于没做）。改为按
**「JD 数 × 组合大小」**排序——量纲上等价于该组合在语料中支撑的"技术-岗位"证据格点数，
同时奖励证据充足与能力集完整。

技术数不足以成组合的 JD 用自身完整技术集兜底，**不伪造也不丢失**。

### 5.3 与既有岗位的距离：非对称覆盖率

判断"新"需要参照系。用**非对称覆盖率**而非 Jaccard：

```
覆盖率 = |候选技术 ∩ 岗位技术| / |候选技术|
```

问的是"候选的能力有多少已被既有岗位吸收"，与岗位自身还要求多少额外能力无关。
Jaccard 会因岗位技术词更多而错误压低覆盖率——候选 {A,B} 面对要求 {A,B,C,D} 的岗位
实际已被完全覆盖，Jaccard 却只有 0.5。

三档分类：`existing_role`(≥0.75) / `role_evolution`(≥0.45) / `potential_new_role`(<0.45)。

**候选粒度直接决定这个测量能不能用。** 候选是技术对时分母恒为 2，覆盖率只能取
0/0.5/1.0 三个值，三档退化成"全覆盖/覆盖一半/不覆盖"，阈值形同虚设：

| | 技术对（旧） | **频繁技术组合（现）** |
| --- | --- | --- |
| 候选大小 | 恒为 2 | 3(31) / 4(8) / 5(2) |
| 覆盖率取值 | {0, 0.5, 1.0} | {0.333, 0.667, 0.750, 0.800, 1.000} |
| 实测分布 | **91/100 恰好等于 1.0** | 三档均有量 |
| 分类结果 | 几乎全判为 existing_role | potential 6 / evolution 29 / existing 65 |

另有两条资格线：技术词少于 2 个的岗位版本不参与比较（能力定义太薄，任何包含该词的组合
与它的重合度都会虚高）；`excluded_role_ids` 支持把指定岗位当作不存在，用于反事实分析。

**跨词表版本必须按技术编码比较。** 节点 id 逐词表版本独立，既有岗位版本的技术要求可能产自
旧词表而候选来自新词表，按 id 比较会得到恒空的交集，于是每个候选都被判成"全新岗位"
（这个 bug 在真跑时暴露：100/100 覆盖率为 0）。技术编码（`T1.03.02` 这类）跨版本稳定。

### 5.4 技术成熟度与证据门控分档

**成熟度**由技术里程碑的时间衰减累积决定：

```
成熟度 = 1 - exp(-α · Σ(类型权重 × 相关度 × exp(-0.35·年龄) × 来源可靠度))
```

类型权重体现证据强度递进：技术演示 0.45 < 论文 0.55 < 专利 0.60 < 工程突破 0.68
< 融资 0.70 < 标准政策 0.72。α=0.17 是实测标定的——早期取 0.85 会让累积量超过 5 的技术
全部压到 0.98 上限（15 个有证据节点里 8 个并列），成熟度这一维失去区分度。

里程碑挂在 L1/L2 而 JD 证据在 L3，因此**无直接证据的节点沿父链继承祖先证据**，
每上溯一层按 0.6 折减，保证有直接证据的节点始终排在继承者前面。
当前 427 条里程碑、9,032 条成熟度快照。

**候选评分**是 8 个正向维度的加权和减去 5 项惩罚：

| 正向维度 | 权重 | | 惩罚项 | 扣分 |
| --- | ---: | --- | --- | ---: |
| publication_task_gap 学术-产业落差 | 0.22 | | 技术未经验证 | 0.20 |
| technology_relevance 技术相关度 | 0.15 | | 纯营销语料 | 0.15 |
| market_support 市场支撑 | 0.14 | | 证据自相矛盾 | 0.12 |
| community_cohesion 社区内聚 | 0.12 | | 单一公司信号 | 0.10 |
| technology_maturity 技术成熟度 | 0.10 | | 单一来源信号 | 0.05 |
| temporal_growth_stability 时序稳定 | 0.10 | | | |
| evidence_completeness 证据完整度 | 0.10 | | | |
| novelty 新颖度 | 0.07 | | | |

**成熟度分档独立于评审流程，纯由证据门控：**

| 档位 | 门控条件 | 当前 |
| --- | --- | ---: |
| `potential` 潜在 | 默认档 | 6 |
| `budding` 萌芽 | 评分≥45 且 JD≥3 份 且 公司≥2 家 且 观测窗≥2 期 且 技术已验证 | 218 |
| `emerging` 涌现 | 评分≥65 且 来源≥2 且 应用证据≥1 且 技术成熟度≥0.35 且 学术产业落差≥0.25 且 观测窗≥3 期 | 3 |

这套门控的意义在于：**"这是个新岗位"是一个需要多重独立证据才能下的结论**，
不是评分高就够。单一公司、单一来源、缺少时序历史都会被显式标记为风险旗标。

### 5.5 表达层：LLM 的位置与边界

**LLM 不得进入任何机械决策路径。** 不由 LLM 决定簇归属、技术编码、评分或分档。
它只有两个合法位置：

1. **表达层改写** — 把机械事实卡（技术组合、代表职责、证据统计）改写成人类可读的
   岗位名称、一句话定义、形成原因、与既有岗位的差异说明。改写结果必须逐条引用机械事实，
   校验不通过则降级为规则模板输出。
2. **离线批处理后物化** — 如技术命中复核，结果落成带版本的数据表，机械流程只读冻结结果，
   不在循环内调用 LLM。

机械事实卡本身可能有误（例如代表职责来自 JD 但语义偏窄），因此卡片带
`task_text_source` 字段标注事实来源（`jd_responsibility` / `technology_fallback`），
交给表达层判断是否采用。

### 5.6 评审与发布

候选进入 `job_discovery` 评审队列，走 claim → approve/reject/needs_revision 工作流。
批准后发布为 `origin_type_code='inference_derived'` 的岗位，与聚类派生岗位并列但可区分。

**候选按稳定键去重。** 键由「推演模式 + 技术组合」派生，同一组合在后续运行中复用既有候选：
终态（已批准/已合并/已驳回）直接跳过，未决状态就地刷新。当前 227 个候选，
最近一次推演新建 27 个、刷新 73 个、跳过 0 个。

## 6. 贯穿性设计约束

这四条约束贯穿所有模块，违反其中任何一条都会让结果不可信：

| 约束 | 落实方式 |
| --- | --- |
| **可重放** | 同输入 + 同算法版本 + 同参数 → 同结果。任何影响输出的输入都进 `input_snapshot_hash` |
| **算法行为变更必须升版本号** | 否则历史运行的重放缓存会串味。本次开发就撞上过：改了排序逻辑没升版，第二次运行直接返回缓存的旧结果 |
| **证据逐字可定位** | 每条技术要求、每项能力变更都挂着 `evidence_span`，含字符偏移与内容哈希 |
| **合成数据显式标记** | JD 观测窗 2/3 为合成日期、里程碑 48 条为估算年份，均有 `time_quality_code` / `data_origin_code` 标记 |
