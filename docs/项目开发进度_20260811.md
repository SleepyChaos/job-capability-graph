## 1. 当前结论

以“可以按挑战杯要求正式评测和交付的 P0 系统”为完成口径，当前总体完成度约为 **65%–70%**，剩余约 **30%–35%**。

当前已经完成的不是纯前端演示，而是以下真实数据和算法底座：

- 原始 XLSX 数据准入、不可变原始行账本和字段映射；
- L1–L4、T1–T7 技术主数据正式发布；
- 真实 JD 入库、去重、技术证据和结构化解析；
- 可重放岗位聚类、稳定岗位候选和岗位版本基础；
- 数据源、采集策略、采集运行、里程碑候选和数据审核的后端契约；
- 自动预测、技术词定向推演、岗位名称推演和新岗位专项审批后端闭环；
- 三类能力图谱真实数据投影及前端交互；
- TXT/粘贴文本简历到画像、匹配、差距和发展路径的 P0 闭环。

剩余工作的主要矛盾已经从“核心表和算法是否存在”转为：

1. 已有后端能力尚未全面接入前端；
2. 真实网页采集、多格式文档和 LLM 等外部适配能力尚未补齐；
3. 官方准确率指标尚无冻结金标准和正式评测结果；
4. 权限、安全、部署和最终演示交付尚未完成。

```text
XLSX 原始数据

→ 正式 JD 与来源版本
→ 技术词命中与语境复核
→ JD 结构化解析
→ 可重放岗位聚类

→ 新岗位推演候选
→ 专项审批

```

该闭环后端已经贯通，但数据中心和新岗位发现前端还没有消费全部真实接口；真实网页持续采集也尚未接入。

### 5.2 能力图谱闭环

```text
最新成功岗位聚类
→ 通过语境复核的技术证据
→ 岗位—能力关系投影
→ 聚类岗位能力重要度与近期活跃
→ 45 天技术触发热力矩阵
→ 前端图谱、详情和表格降级
```

该闭环已经接入真实数据库。当前限制来自源时间覆盖，而不是图谱页面使用 Mock。

### 5.3 人岗匹配 P0 闭环

```text
TXT / 粘贴文本
→ 简历事实和技术别名匹配
→ L3 标准能力证据
→ 2–8 轮自适应追问
→ 用户确认画像版本
→ 岗位聚类召回与机械精排
→ 逐能力差距
→ 绑定 gap ID 的发展路径
```

该闭环不依赖 LLM Provider，匹配分数可以回放，画像修改生成新版本，不覆盖历史结果。

## 7. 后续四个开发阶段

继续遵循“每完成一个阶段形成一个 commit”的约定。

### 下一阶段 A：数据中心全面去 Mock

目标：将数据中心主页、数据采集中枢、数据管理中心、技术词标准管理和数据审核中心接入现有真实 API。

完成条件：

- 页面统计来自当前数据库；
- 数据源、JD、技术词和审核任务可真实查询；
- 支持的写操作必须保存到后端并保留审计；
- 未实现操作明确禁用或标注，不显示虚假成功提示；
- 删除对应页面对 `mockData.ts` 的业务依赖。

### 阶段 B：新岗位发现全面去 Mock

目标：接通自动预测、技术词定向推演、岗位名称推演和推演结果记录库。

完成条件：

- 三种模式调用真实推演运行接口；
- 候选列表、评分、风险和证据来自冻结运行快照；
- 专项审批真实创建岗位版本和标准 JD；
- 记录库展示真实运行、候选、定义版本和处置状态；
- 系统总览改为聚合真实数据。

### 阶段 C：外部适配与多模态增强

目标：补齐真实采集器、多格式简历、文件安全和 LLM Provider。

执行顺序：先真实采集和 PDF/DOCX 文本解析，再 OCR 和文件安全，最后接入受约束的 LLM 表达与语义能力。LLM 不进入机械评分，也不得直接发布事实。

### 阶段 D：评测、安全与最终交付

目标：冻结测试集、校准算法、验证官方指标，完成部署和演示材料。

完成条件以原计划阶段 8 为准；在金标准建立前，不宣称 JD 解析、简历技能提取或人岗匹配准确率达到 90%。
