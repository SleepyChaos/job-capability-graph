# 数据采集中枢与里程碑审核闭环实现验收报告

日期：2026-08-11
阶段：采集公共契约、里程碑候选和统一数据审核底座（已完成）

## 1. 阶段结论

本阶段已经跑通“维护数据源与采集策略 → 创建采集批次 → 记录页面请求 → 保存来源材料版本 → 抽取里程碑候选 → 绑定原文证据 → 进入数据审核队列 → 审核发布”的纵向闭环。

现有数据包中没有独立、可验证的技术里程碑数据，因此本阶段没有导入或虚构正式里程碑。自动化验收使用域名为 `example.invalid`、技术编码以 `SYNTH-` 开头且正文明确声明仅供测试的合成材料。当前生产数据中的已验证里程碑数量仍为零，必须等待真实公开材料进入采集流程后才能增长。

## 2. 已实现范围

### 2.1 数据采集中枢公共底座

- 数据源登记、查询及默认可信度；
- 采集策略版本、时区、频率、并发、允许范围和解析器标识；
- 最大深入层级由接口和数据库共同限制为一层；
- `robots` 为限制或禁止时，不能创建启用的自动采集策略；
- 采集运行批次及发现、变更、未变更、失败计数；
- 每个请求保存 URL 哈希、层级、类型、状态、重试、响应摘要和解析状态；
- 相同运行内相同 URL 幂等，不产生重复请求记录。

本阶段提供的是采集器统一使用的数据契约和留痕机制，不包含绕过登录、验证码或访问控制的实现，也尚未接入定时 Worker 和具体网站适配器。

### 2.2 里程碑候选和证据

候选提交必须包含来源、来源记录键、URL、标题、正文、时间、事件名称、类型、年份或日期、说明、证据原文和标准技术编码。系统执行以下机械校验：

1. 来源存在且启用；
2. 事件日期与年份一致；
3. 技术编码存在于启用的技术词主数据；
4. 证据引文必须是正文中的连续文本；
5. 保存证据的起止字符偏移和哈希；
6. 按来源与来源记录键维护文档身份，按正文哈希维护内容版本；
7. 同一内容版本中的同一候选事实重复提交时返回已有候选；一份材料可支持多条不同事实。

候选评分保存来源可靠性、抽取置信、完整度、证据覆盖、跨来源确认、时效性和一致性七项分量。由于里程碑会直接影响技术成熟度和新岗位评分，首版无论总分高低都必须人工审核；分数仅用于队列优先级，不能越过审核自动发布。

### 2.3 统一数据审核

- 数据审核队列使用 `queue_code=data_review`，与后续新岗位专项审批分离；
- 支持领取、通过、驳回和退回修改；
- 校验审核状态迁移，禁止终态任务重复决策；
- 审核人必须是系统中启用的 `reviewer` 或 `admin`；
- 每次动作保存操作人、评论、前后状态以及目标前后快照；
- 通过后候选事实变为已发布，里程碑变为已验证，技术关系变为人工确认；
- 驳回后候选事实和里程碑均保留记录但不能进入正式计算。

API 当前通过 `X-Reviewer-Code` 把请求映射到数据库中的审核账号。这只是开发阶段的身份桥接，不接受任意显示名称作为审核人；正式部署阶段必须替换为登录令牌和权限中间件。

## 3. 数据库变化

迁移 `20260811_0004` 新增 13 张表：

| 分组 | 表 |
| --- | --- |
| 身份 | `app_user` |
| 采集 | `md_source_collection_policy`、`biz_collection_run`、`biz_collection_request` |
| 抽取与验证 | `biz_extraction_run`、`biz_extracted_fact`、`rel_fact_evidence`、`biz_fact_validation` |
| 审核 | `biz_review_task`、`biz_review_action` |
| 里程碑 | `biz_milestone_event`、`rel_milestone_technology`、`rel_milestone_evidence` |

里程碑材料复用已有 `raw_source_document`、`raw_source_document_version` 和 `biz_evidence_span`，避免为每种事实重复建设来源、版本和证据体系。

## 4. API 清单

- `POST/GET /api/v1/sources`：数据源登记和查询；
- `POST/GET /api/v1/collection-policies`：采集策略登记和查询；
- `POST/GET /api/v1/collection-runs`：采集运行创建和查询；
- `POST /api/v1/collection-runs/{run_code}/requests`：请求留痕；
- `POST /api/v1/milestones/candidates`：提交结构化里程碑候选材料；
- `GET /api/v1/milestones`：按验证状态查询里程碑；
- `GET /api/v1/milestones/{milestone_code}`：查看候选或正式里程碑；
- `GET /api/v1/reviews/data`：查看数据审核队列；
- `POST /api/v1/reviews/data/{task_code}/actions`：领取、通过、驳回或退回修改。

## 5. 自动化验收结果

- Ruff 静态检查通过；
- 全量自动化测试 13 项通过；
- 合成闭环覆盖来源、策略、运行、请求、候选、幂等、证据、未认证拦截、审核发布和审计动作；
- 不在正文中的证据引文会被拒绝；
- 全新 SQLite 数据库可从空库升级到 `20260811_0004`；
- `alembic check` 无未生成的模型差异；
- 从 head 降级到 base 后可再次完整升级。

## 6. 尚未完成与后续接入

以下内容不应被误认为已经完成：

- 没有真实里程碑数据，正式里程碑仍为零；
- 尚未实现招聘网站、企业官网和政府网站的具体采集适配器；
- 尚未接入 Redis、定时 Worker、限流执行器和失败重试执行器；
- 本阶段只跑通里程碑候选，JD 增量候选和技术词候选仍需接入统一事实与审核框架；
- 多来源事件合并与交叉验证尚未实现，因此评分中的跨来源确认项为零；
- 审核修改字段和候选合并动作尚未开放；
- 正式认证、细粒度权限和审计导出留待安全与交付阶段。

下一阶段可以开始正式岗位聚类和既有岗位演化；同时把真实采集器作为独立适配层接入本阶段契约。新岗位发现只允许消费审核通过的里程碑，不能读取候选状态记录。
