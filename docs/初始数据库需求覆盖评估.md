# 初始数据库需求覆盖评估

> 评估对象：`具身智能产业图谱_情景驱动数据库_MySQL8.sql`
> 数据库：MySQL 8.0.16+
> 评估基线：《项目开发需求文档》《项目总体设计方案》《后端逻辑与数据流设计》
> 评估性质：静态架构审查，不代表 SQL 已在真实 MySQL 环境完成迁移和性能验证

## 1. 总体结论

该 SQL 共定义 **137 张表、11 个面向页面/API的视图**，已经覆盖大量产业图谱、岗位、人才、技术、证据、审核和评测对象。对挑战杯方案而言，它不是空白初始库，而是一份覆盖面较高的融合业务库。

但数据库的“实体覆盖”明显高于“流程可执行覆盖”。当前最主要的问题不是少几张基础业务表，而是以下关键链路尚未形成严格的数据模型：

1. 采集策略、定时调度、URL 发现和每次请求的运行记录；
2. 独立于 L1–L4 的 T1–T7 技术领域轴；
3. 岗位聚类运行、成员历史和拆分/合并谱系；
4. 求职者画像版本、对话和2–8轮问答；
5. 生成标准 JD 与真实 JD 的物理隔离；
6. 45天热力图需要的按日触发指标；
7. 匹配的画像版本输入和逐维度评分明细；
8. 任务幂等、Outbox 和审核工作队列。

按本报告的加权审查口径，当前总体需求覆盖率约为 **72%**：

- 核心实体覆盖：约 85%；
- 端到端业务流转覆盖：约 60%；
- 图谱与算法可计算覆盖：约 65%；
- 证据、审核、评测和隐私覆盖：约 85%。

这里的百分比是架构评审估计，不是官方准确率指标。补齐 P0 缺口后，结构覆盖可提升到 90% 以上。

## 3. 已经覆盖较好的部分

### 3.1 原始数据、版本和质量

现有表：

- `md_data_source`；
- `biz_import_batch`、`stg_import_row`、`biz_import_field_mapping`；
- `raw_document`、`raw_document_version`；
- `biz_document_quality`；
- `biz_duplicate_cluster`、`rel_duplicate_cluster_member`。

优点：

- 区分稳定文档和文档版本；
- 使用内容哈希避免同文档重复版本；
- 使用生成列约束每个文档最多一个当前版本；
- 对时效、噪声、重复、能力通胀、AI生成风险和完整性进行质量评分；
- 保留近重复簇和代表文档，符合官方对复制、噪声和时滞治理的要求。

### 3.2 L1–L4 技术词主数据

现有表：

- `md_technology_taxonomy_version`；
- `md_technology_node`；
- `md_technology_alias`；
- `md_technology_mapping_rule`；
- `biz_technology_mapping_run/result`；
- `biz_technology_term_candidate`；
- `biz_technology_migration_audit`。

优点：

- 支持 L0–L4 统一树节点、主数据版本、别名、正则、人工映射和候选池；
- 未命中词审核前禁止进入正式匹配；
- 支持合并、拆分、重命名和弃用的迁移审计；
- 原始词、标准词、规则和置信度都有留痕。

### 3.3 正式岗位、能力版本和演化

现有表：

- `md_job_direction`；
- `biz_job_direction_version`；
- `biz_job_direction_assignment`；
- `rel_direction_version_capability`；
- `md_application_scenario`、`rel_direction_version_scenario`；
- `biz_job_evolution_event`、`biz_job_evolution_change`；
- `biz_job_period_metric`、`biz_capability_period_metric`、`biz_capability_cooccurrence_metric`。

优点：

- 正式岗位和岗位版本分离；
- 每个岗位最多一个已批准当前版本；
- JD 到岗位版本的分配保留历史；
- 岗位能力保存必需/加分/前沿、重要度、级别、企业数、来源数和置信度；
- 可明确记录 added、removed、modified；
- 有周期热度、能力趋势和共现指标。

### 3.4 新岗位发现

现有表：

- `biz_new_job_discovery_run`；
- 三类运行输入快照关系；
- `biz_emerging_job_candidate`；
- 候选与 JD、技能、能力、技术、里程碑和证据的关系；
- 审批后回指 `md_job_direction`。

优点：

- 冻结时间窗、数据版本、算法、模型、Prompt 和参数；
- 保留实际输入 JD、关键词和里程碑清单；
- 候选包含新颖度、增长、稳定、跨源和幻觉风险；
- 记录独立企业数、来源数和支撑 JD 数；
- 候选技能、能力、技术和里程碑均可独立解释；
- 通过审核后进入与既有岗位同级的正式岗位表。

### 3.5 证据和幻觉防控

现有表：

- `biz_extraction_run`；
- `biz_evidence_span`；
- `biz_extracted_fact`、`rel_fact_evidence`；
- 正式岗位版本和能力证据关系；
- `biz_fact_validation`；
- `biz_human_review`。

优点：

- 抽取任务可绑定模型、Prompt、本体和 RAG 状态；
- 事实验证前不得进入正式图谱；
- 支持支持证据和反证；
- 可统计独立机构、独立来源和冲突数；
- 人工审核保存前后 JSON。

### 3.6 匹配、学习路径和评测

匹配、逐能力差距、学习资源、路径、步骤依赖、基准数据集、测试用例、评测运行和指标均有对应表，能够支撑官方三项90%指标的结果存档。

## 4. P0 缺口与改造建议

### 4.1 采集中枢缺少真实运行模型

`md_data_source` 目前只保存来源名称、类型、URL、权威度和可靠度，不能支持前端设计中的规则维护、调度、分页、一级深入、限速和运行监控。

建议新增：

```text
md_source_crawl_policy
  source_id, list_rule_json, detail_rule_json, max_depth,
  pagination_rule_json, rate_limit, robots_status,
  terms_checked_at, allowed_scope, parser_code

biz_crawl_schedule
  source_id, cron_expression, timezone, next_run_at,
  enabled, failure_backoff_policy

biz_crawl_run
  source_id, scheduled_at, started_at, completed_at,
  status, discovered_count, changed_count, error_count

biz_crawl_request
  crawl_run_id, parent_request_id, url, depth,
  response_status, response_hash, storage_object_key,
  retry_count, parse_status, error_code
```

`biz_import_batch/stg_import_row` 可以继续用于 Excel 导入，但不应承担所有网页采集语义。

### 4.2 T1–T7 与 L1–L4 尚未真正分离

当前 SQL 只有通用 `md_domain`，`md_technology_node` 没有到 T1–T7 的结构化多对多关系。`cross_domain_trace` 文本不能支持筛选、领域占比和证据计算。

建议：

```text
md_technology_domain
  technology_domain_id, domain_code(T1-T7), name,
  definition, color_token, sort_order, version

rel_technology_node_domain
  technology_id, technology_domain_id, domain_score,
  is_primary, evidence_count, calculation_version, review_status

rel_job_cluster_domain
  job_cluster_version_id, technology_domain_id, domain_score,
  is_primary, evidence_count, calculation_version, review_status

rel_job_direction_version_domain
  job_direction_version_id, technology_domain_id, domain_score,
  is_primary, evidence_count
```

这是图谱统一颜色、T域筛选和岗位领域划分的 P0 表，不建议使用 JSON 代替。

### 4.3 岗位聚类模型不完整

`md_job_cluster` 只有名称、描述和算法版本；`biz_job_posting.job_cluster_id` 会覆盖当前归属，无法记录每次聚类、成员分数和聚类谱系。

建议新增：

```text
biz_job_clustering_run
  time_window, input_snapshot, feature_version,
  algorithm_version, parameters, status, metrics

biz_job_cluster_version
  clustering_run_id, stable_cluster_code, label,
  centroid_object_key, member_count, quality_score

rel_job_cluster_member
  cluster_version_id, job_id, similarity_score,
  assignment_method, is_current, top_candidates_json

rel_job_cluster_lineage
  from_cluster_version_id, to_cluster_version_id,
  lineage_type(continued/split/merged/born/ended), overlap_score

rel_job_cluster_role
  cluster_version_id, job_direction_id, relation_type, confidence
```

同时明确：`biz_job_direction_assignment` 是 JD 到正式岗位版本的权威关系；`biz_job_posting.job_direction_id/job_cluster_id` 只能作为查询缓存或移除，避免双写漂移。

### 4.4 缺少标准 JD 独立实体

候选表的 `output_snapshot_json` 可以保存模型输出，但无法管理多份标准 JD、组织条件、人工修订和审批，也容易与真实 JD 混淆。

建议新增：

```text
biz_generated_job_description
  generated_jd_id, job_direction_version_id, context_json,
  generation_model, prompt_version, status, created_by

biz_generated_job_description_version
  generated_jd_id, version_no, content_json, content_text,
  previous_version_id, edit_source, approved_by, approved_at
```

并在数据库约束和统计查询中明确它不能进入 `biz_job_posting` 和真实招聘指标。

此外，`biz_new_job_discovery_run` 目前不能明确区分自动预测、技术词定向推演和岗位名称推演，也没有保存岗位名查询文本。建议增加：

```text
run_mode_code(auto/keyword/name)
query_text
query_normalized
requested_candidate_stage
```

`biz_emerging_job_candidate` 还应增加独立于审核状态的 `candidate_stage_code`（potential/budding/emerging/confirmed）和综合候选分。`pending/reviewing/approved` 是工作流状态，不能代替岗位成熟阶段。

### 4.5 简历不等于求职者画像

当前有 `biz_resume`、`md_talent`、`rel_talent_capability`，但缺少页面逻辑要求的画像实体、事实/洞察分层、历史画像和2–8轮问答。

建议新增：

```text
biz_candidate_profile
  profile_id, owner_user_id, profile_group_code, current_version_id

biz_candidate_profile_version
  profile_version_id, profile_id, version_no, resume_id,
  previous_version_id, status, target_role_text,
  facts_json, insights_json, model_version, user_confirmed_at

biz_profile_experience / biz_profile_project / biz_profile_education
rel_profile_version_capability
rel_profile_version_preference

biz_profile_conversation
biz_profile_message
biz_profile_question
biz_profile_answer
```

每项事实和能力需绑定简历证据或用户回答。洞察保存 `inference`/`confirmed` 状态，不能混入事实。

### 4.6 当前简历分析运行与用户流程耦合错误

`biz_resume_analysis_run.match_request_id` 为必填，并把“简历技能提取、差距分析与修改建议”合在一次运行中。但产品流程要求先解析并入库画像，之后用户选择画像才执行匹配。

建议拆分：

- `biz_resume_parse_run`：只绑定简历版本；
- `biz_profile_build_run`：绑定简历和会话；
- `biz_match_run`：绑定画像版本和目标版本；
- `biz_match_explanation_run`：绑定匹配结果；
- 简历修改建议若保留，作为匹配后的独立输出。

### 4.7 匹配没有冻结画像版本

`biz_match_request` 当前只绑定 `resume_id`，无法保证历史匹配使用的是哪一版求职者画像。应增加必填 `candidate_profile_version_id`，`resume_id` 仅用于追溯。

同时建议新增：

```text
biz_match_dimension_result
  match_result_id, dimension_code, raw_score,
  weight, contribution, confidence, explanation
```

当前 `required_score/bonus_score/frontier_score` 不能完整表达项目证据、时间新鲜度、场景、级别、可迁移能力和偏好等多维结果。

### 4.8 热力图缺少按日触发数据

`biz_capability_period_metric` 以 week/month/quarter/year 周期统计，无法直接稳定输出45个日格。

建议新增：

```text
biz_technology_daily_trigger_metric
  metric_date, technology_domain_id, technology_id,
  trigger_document_count, trigger_mention_count,
  independent_org_count, independent_source_count,
  calculation_version
```

必要时另建文档级明细关系，用于点击热力格查看当天触发材料。

### 4.9 里程碑没有候选/审核状态和文档版本

`biz_milestone` 直接表示正式事件，只有 `source_id/source_url`，缺少 `document_version_id`、抽取运行、候选状态、置信度和审批人。

建议增加里程碑候选表，或为现表增加：

```text
document_version_id
extracted_fact_id
verification_status
confidence_score
approved_by / approved_at
superseded_by_id
```

只有已验证里程碑进入新岗位评分。

### 4.10 审核表不是完整工作队列

`biz_human_review` 能保存最终审核结果，但缺少待办状态、分配、优先级、领取、SLA、退回和重审。

建议新增统一 `biz_review_task`，再用现有 `biz_human_review` 保存每次决策记录。数据审核和新岗位专项审批使用不同 `queue_code`。

### 4.11 缺少任务 Outbox 和统一幂等

数据库目前有多种运行表，但没有统一任务尝试、幂等请求和事务 Outbox。建议新增：

```text
sys_async_task / sys_task_attempt
sys_idempotency_record
sys_outbox_event
sys_dead_letter_task
```

它们用于保证任务重试不重复入库，并确保发布岗位版本后图谱、搜索和缓存最终一致。

### 4.12 原始文件资产模型不足

`raw_document_version` 保存正文，但没有对象存储键、MIME、文件大小、病毒扫描、OCR 产物和下载校验等字段。建议增加 `raw_file_asset`，由文档版本或简历引用。

## 5. 需要修正的结构风险

### 5.1 技术编码和版本约束冲突

`md_technology_node.tech_code` 当前是全局唯一，但表又允许多个 `taxonomy_version`。同一个技术编码无法自然出现在新旧两个词表版本。

建议改为：

```text
UNIQUE (taxonomy_version, tech_code)
```

并保证父节点与子节点属于同一 taxonomy version。可通过复合外键或服务层事务校验完成。

### 5.2 nullable 列上的唯一键无法阻止全局指标重复

MySQL 唯一索引允许多行 NULL。以下唯一键在 `job_direction_id IS NULL` 时不能保证全局指标唯一：

- `biz_capability_period_metric(analysis_period_id, capability_id, job_direction_id)`；
- `biz_capability_cooccurrence_metric(analysis_period_id, job_direction_id, capability_a_id, capability_b_id)`。

建议增加生成列，把 NULL 映射为固定哨兵值后建立唯一索引，或把全局统计与岗位内统计拆表。

### 5.3 原始文档业务键为空时可重复

`raw_document` 的 `(source_id, source_record_key)` 在 `source_record_key IS NULL` 时允许重复。网页没有来源业务 ID 时，应使用规范化 URL 或生成的 `document_identity_key`，并建立非空唯一键。

### 5.4 抽取运行的任务对象不一致

`biz_extraction_run.document_version_id` 必填，但 `task_type_code` 包含 `role_define`。岗位定义通常由多份 JD、里程碑和统计快照共同产生，不能绑定单一文档。

建议让该表只承载文档抽取，岗位定义使用 `biz_new_job_discovery_run`/独立生成运行；或者改成通用主体并增加运行输入关系表。

### 5.5 正式岗位存在双重当前关系

`biz_job_posting` 上有 `job_direction_id/job_cluster_id`，又有 `biz_job_direction_assignment` 历史表。两者可能不一致。必须冻结一个权威来源；建议历史分配表为权威，Posting 列仅作缓存并由同一事务维护。

### 5.6 岗位级别筛选缺少正式岗位版本字段

`biz_job_posting.ability_level_code` 可表达单条 JD 级别，`rel_direction_version_capability.required_level_code` 表达技能要求级别，但正式岗位版本没有明确的岗位级别分布或主级别。

建议新增岗位版本级别关系或指标：

```text
rel_job_direction_version_level
  job_direction_version_id, job_level_code,
  coverage_rate, jd_count, is_primary
```

以支持“岗位级别”和“技能级别”两类切换。

### 5.7 证据文本字段与正式证据关系并存

多张早期关系表使用 `evidence_text`，赛题增量又引入规范化 `evidence_span_id`。建议将 `evidence_span` 关系作为权威证据，文本字段只作缓存或兼容，避免证据内容修改后不一致。

### 5.8 技术词、技能和能力三套主数据的边界尚未冻结

当前同时存在 `md_technology_node`、`md_skill` 和 `md_capability`，并通过多张映射表连接。结构允许兼容旧数据，但如果没有统一语义，JD抽取、岗位版本、图谱和匹配会使用不同粒度。

建议冻结以下职责：

- `md_technology_node`：L1–L4 技术标准体系；L3 是技术图谱默认技术点，L4 是识别和证据表面词；
- `md_skill`：外部技能字典或兼容标签，不作为最终图谱权威节点；
- `md_capability`：包含技术能力、任务能力和通用能力的匹配本体；
- 技术类 capability 必须映射到一个或多个 L3 节点，并保存主映射和置信度；
- 岗位图谱若展示“标准技术点”，应直接按 L3 投影；匹配可以继续按 capability 计算。

如果正式岗位能力以 capability 为唯一权威关系，应补充岗位版本到 L3 技术点的可复现投影视图或日聚合；如果技术要求需要独立统计，则增加 `rel_direction_version_technology`，不要在 API 中临时拼接三套定义。

## 6. 不建议首期继续扩展的部分

数据库包含企业融资、高校、论文、专利、政策、标准、成果和机构推荐等丰富对象。它们可以作为技术里程碑、应用落地和多源证据，但不是完成比赛闭环的第一优先级。

首期建议：

- 保留这些表，不删除；
- 只选择能支撑一个新岗位样例的少量数据接入；
- 暂不继续扩展复杂的企业—高校联合推荐；
- 优先把 JD、岗位、能力、图谱、画像和匹配的纵向链路跑通。

## 7. 推荐改造顺序

### P0：影响闭环正确性

1. 采集策略、调度、运行和请求表；
2. 独立 T1–T7 领域及技术/聚类/岗位版本关系；
3. 聚类运行、成员历史和谱系；
4. 标准 JD 独立实体；
5. 求职者画像版本、经历/项目/偏好和对话问答；
6. 匹配绑定画像版本及逐维度评分；
7. 按日技术触发指标；
8. 里程碑候选审核；
9. 审核任务、Outbox 和幂等；
10. 修复技术版本唯一键和 nullable 唯一键风险。

### P1：提高可解释性和性能

1. JD 职责、场景、能力的逐项结构表和证据关系；
2. 岗位级别分布；
3. 聚类 Top-K 候选和人工校准记录；
4. 图谱投影缓存和每日/周期快照；
5. 技术词、岗位和画像的向量版本记录；
6. 数据删除后的派生结果失效和重算记录。

### P2：研究扩展

1. 独立图数据库；
2. 大规模流式图谱更新；
3. 企业、高校、成果和岗位的联合推荐；
4. 多领域迁移和跨行业验证。

## 8. 最终判断

这份数据库适合作为新后端的**领域数据底座**，尤其可以复用：原始文档版本、质量和去重、L轴技术词治理、新岗位运行和证据、岗位能力版本、演化事件、匹配差距、学习路径和评测表。

它暂时不适合作为不经修改的最终生产结构。若直接开发，最容易在四处返工：采集任务无处落、T轴只能写文本、聚类历史被覆盖、简历解析后找不到真正的画像版本。建议先完成 P0 数据库迁移设计，再开始真实后端接口和 Worker 实现。
