# 数据库迁移计划：以 project-export 数据为主体

> **文档版本**：v1.1（已执行，实测结果回填）
> **编制日期**：2026-08-06
> **文档定位**：将 project-export（项目二）真实数据资产整体迁入统一库 `db/unified.db`，使其成为系统的主体数据源。配套修订见《开发文档.md》阶段 2.5；统一库表结构见 `db/schema.sql` 与《数据库设计.md》。

---

## 1. 背景与目标

阶段 0/1 建库时以 120 条合成样例 JD 走通管线，统一库当前仅有演示级数据。用户明确要求：**以 project-export 的技术词分类、JD 数据、职业（聚类/人才）数据为主体**重新组织数据。本计划即迁移方案。

**目标**：
1. project-export `data/jobs.db` 的 9 张表全量、幂等地迁入统一库；
2. 技能本体按项目二的技术词分类体系落地（L1→L2 挂载 + L4 四类型：细分词/组合词/指标词/型号词）；
3. 迁移后统一库成为后端 API 与前端展示的唯一主体数据源，样例数据保留作回归测试集。

## 2. 源数据盘点（已实测）

源库：`existing-projects/project-export/data/jobs.db`（具身智能领域）

## 3. Schema 调整（在现有 16 表上做增量修订）

| 表 | 修订 | 原因 |
|---|---|---|
| `skills` | `l4_type` 取值扩展为 **细分词/组合词/指标词/型号词**（补"型号词"）；`source` 增加取值 `'embodied_db'`（源库迁移词） | 对齐项目二原版四类词设计；区分迁移词与词典词 |
| `job_skills` | `evidence` 允许为空并注释"源库无证据，可选重提取回填"；新增 `keyword_raw` 列（源词原始写法） | 源库关联不带 JD 证据片段，证据回填是阶段 4 幻觉防控的工作 |
| `resumes` | 新增人才画像列：`talent_type` / `university` / `school_lab` / `research_direction` / `achievements` / `industry` | 映射 talents 表画像字段，阶段 3 人岗匹配直接使用 |
| 其余表 | 不动 | jobs/clusters/job_cluster_map/cluster_classifications/resume_skills 已同构 |

修订方式：直接改 `db/schema.sql`（建表语句 + 注释），重建库后由管线+迁移脚本重新填充，不做 in-place ALTER。

## 4. 迁移映射与步骤

实现为 `pipeline/migrate_project_export.py`（幂等、可重复执行，依赖标准库 sqlite3；用 `ATTACH DATABASE` 跨库读写）：

### 步骤 1：技能本体（domains / l2_categories / skills）
- domains：T1–T7 已在阶段 1 随 `embodied_terms.csv` 导入，幂等跳过；
- l2_categories：以源库 `job_keywords` 的 `DISTINCT (l1_code, l2_name)` 补齐缺失 L2（统一库现有 65 个以词典为准，源库多出的 L2 自动补录）；
- skills：源库 197 个规范词 upsert（按 `skill_term` 唯一）；`l4_type` 如实记"细分词"，在数据契约中注明"源库词典降级，四类标注以 `assets/embodied_terms.csv` 修订版为准"。

### 步骤 2：岗位（jobs）
- 10,447 条全量映射（字段同名直迁）；`dedup_key` 按既有规则（title+company+collect_time 归一化）计算后 upsert；
- 与既有 120 条样例 JD 天然共存（dedup_key 不冲突）。

### 步骤 3：岗位-技能关联（job_skills）
- 12,309 条映射：`keyword_norm → skill_id`、`l4_type` 直迁、`confidence=0.95`（词典匹配默认值）、`source='dictionary'`、`evidence=NULL`；
- **证据回填（可选，默认开启）**：用阶段 1 移植的 `pipeline/extract.py` 正则对 `jd_text` 重跑匹配，回填 `evidence` 片段——源库词表仅 197 个，10,447 JD 重提取耗时可控（多进程）。此步同时验证移植提取器在真实数据上的命中一致性。

### 步骤 4：聚类三表
- clusters / job_cluster_map / cluster_classifications 直迁（cluster_id 原样保留）；
- 未聚类的约 5,471 岗位保持未聚类状态，是否增量补聚类由阶段 5 案例需求决定（**不在本次迁移范围**，避免与源聚类结果口径混杂）。

### 步骤 5：人才简历（resumes / resume_skills）
- talents → resumes：画像字段映射到新增列，`resume_id` 沿用 `talent_id`，`raw_text=resume_text`；
- talent_keywords → resume_skills：`keyword_norm → skill_id`，库内无对应词时跳过并计数上报（预计接近全覆盖，词表同源）。

### 步骤 6：数据质量校验（迁移脚本内置，失败即回滚退出）
1. 行数核对：jobs / job_skills / clusters / job_cluster_map / resumes 迁入数 = 源库数（去重冲突除外，冲突数单独上报）；
2. 引用完整性：job_skills.skill_id、job_cluster_map.job_id、resume_skills.skill_id 无悬空；
3. L1 分布核对：迁入后按 l1_code 的岗位数与源库一致；
4. 抽查：随机 10 条 job_skills 的 keyword_raw 与源库逐字段一致。

## 5. 迁移后影响与适配

| 受影响 | 适配内容 | 归属阶段 |
|---|---|---|

| 阶段 3 测试集 | 175 份真实简历 + 897 条人才技能词成为简历提取/匹配的现成测试集（≥90% 准确率验证） | 阶段 3 受益 |

## 6. 回滚与兼容

- 迁移脚本不修改源库（只读 ATTACH）；统一库迁移前自动备份为 `db/unified.db.bak-<日期>`；
- 样例 JD 与合成聚类保留在库内，`pipeline_meta` 记录数据批次（source_file 区分 `sample` / `project-export`），前端若需纯演示口径可按来源过滤；
- 迁移为幂等 upsert，中断后重跑不产生重复。

## 7. 完成标准

1. `python3 -m pipeline.migrate_project_export` 一键完成且内置校验全部通过；
2. 后端 API 在真实体量下响应正常（/api/graph 聚合模式、/api/clusters 分页）；
3. 前端图谱/热力/发现三页在真实数据下渲染通过（热力图含具身域 embodied）。

## 8. 实测执行结果（2026-08-06）

> 与原计划的主要差异：**源库存在大量同 title+company+collect_time 的重复 JD**，
> dedup_key 幂等去重后 10,447 → **6,673**；被合并岗位的关联边与聚类成员全部改指幸存者，口径无丢失（脚本内置“岗位无丢失”校验通过）。

| 指标 | 迁移前 | 迁移后 |
|---|---|---|
| jobs | 120（样例） | **6,793**（源库去重 6,673 + 样例 120） |
| job_skills | 1,071 | **16,925**（源库关联合并后 + 证据回填补边 8,928） |
| skills | 389 | **505**（含人才库特有指标词 113 个补入本体） |
| clusters | 47 | **1,680**（源库 1,633 + 样例 47） |
| resumes | 0 | **175**（resume_skills 897 条全覆盖） |
| 证据回填 | - | 6,130 条回填 + 8,928 条新命中边（移植提取器在真实数据上的增量命中） |

执行中修正的三个问题：① 源库重复 JD 合并映射（关联/聚类改指幸存者）；② 人才库 113 个特有词条（多为基准名/指标词）补入技能本体；③ 源库聚类 JSON 字段实为逗号分隔串，后端加容错解析。迁移前自动备份（`db/unified.db.bak-*`），全程幂等可重跑。
