# 测试数据集设计方案 v1

> 项目：多源异构数据驱动的具身智能岗位和能力图谱构建与动态演化分析平台
>
> 版本：v1.0-draft
>
> 日期：2026-08-10
> 定位：在正式开发前冻结测试数据的类型、模板、样例、标注和评测口径；本文描述数据设计，不代表样本已经完成标注。

## 1. 设计结论

测试数据不应等同于“放 100 条 JD 供系统演示”。为了同时满足挑战文件、算法评测、闭环演示和工程验收，建议建立三层测试资产：

1. **量化金标准集**：用于计算 JD 解析、简历技能提取和人岗匹配三项核心指标；
2. **业务闭环场景包**：分别覆盖一个新岗位和一个既有岗位，从数据源、处理过程到能力图谱和输出结论全程可追溯；
3. **工程与风险测试夹具**：覆盖清洗、去重、时序、幻觉、提示词注入、权限、性能和失败恢复，不参与三项核心准确率统计。

推荐首版规模如下：

| 数据资产 | 推荐规模 | 官方最低要求关系 | 主要用途 |
| --- | ---: | --- | --- |
| JD 开发集 | 30 条 | 不计入最终 100 条测试集 | 调整规则、提示词和字段映射 |
| JD 冻结测试集 | 120 条 | 覆盖“至少 100 条岗位 JD 及测试用例” | JD 解析主评测 |
| 简历开发集 | 20 份 | 官方未限定数量 | 调整解析与技能归一化 |
| 简历冻结测试集 | 100 份 | 支撑简历提取准确率 ≥90% | 多格式简历评测 |
| 人岗匹配金标准 | 300 对 | 支撑匹配准确率 ≥90% | 三分类、差距识别和排序评测 |
| 新岗位闭环场景 | 2 组，至少 1 组完整交付 | 官方要求至少 1 个 | 新岗位发现、定义、审核、图谱发布 |
| 既有岗位更新场景 | 2 组，至少 1 组完整交付 | 官方要求至少 1 个 | 能力新增、修改、淘汰和热度变化 |
| 数据治理与幻觉集 | 80 例 | 支撑创新性和可信性说明 | 噪声、转载、冲突、缺证据和注入测试 |
| 图谱与 45 天聚合集 | 1 组固定日序列 | 支撑图谱功能验收 | 节点、边、重要度、活跃度和边界测试 |
| 性能合成集 | 1 万 JD 起 | 非官方数量要求 | 批处理、查询和图谱加载性能 |

这里将 JD 最终测试集设为 120 条而不是恰好 100 条，原因是开发样本不能混入最终测试，且应为无效文件、争议标注和抽检保留余量。

## 2. 官方要求对应关系

挑战文件对测试相关交付提出以下明确要求：

| 官方要求 | 本方案落实方式 |
| --- | --- |
| 完整测试方案，含至少 100 条岗位 JD 及测试用例 | 建立 120 条冻结 JD 金标准，每条绑定至少一个解析测试用例 |
| JD 解析准确率 ≥90% | 使用字段级人工金标准，报告综合得分、各字段 Precision、Recall、F1 和错误样本 |
| 简历提取准确率 ≥90% | 使用 100 份脱敏或合成多格式简历，技能结果必须绑定原文证据 |
| 匹配准确率 ≥90% | 冻结岗位—画像三分类金标准，同时补充 Macro-F1、NDCG@5 和差距项 F1 |
| 单元测试覆盖率 ≥60% | 工程测试用例与评测数据分开管理，由覆盖率工具生成报告 |
| 1 个新岗位的能力图谱及岗位数据源 | 提交新岗位闭环场景包，保存来源、输入、中间证据、输出和图谱快照 |
| 1 个既有岗位的能力图谱及岗位数据源 | 提交既有岗位演化场景包，保存两个以上时间窗及变更依据 |
| 对应输入输出示例 | 每个场景提供可直接导入的输入文件、期望结果和人工说明 |

必须特别区分两件事：

- “至少 100 条 JD”是量化测试集要求；
- “1 个新岗位和 1 个既有岗位”是完整业务场景交付要求。

两者不能用同一张汇总表简单替代。

## 5. JD 解析金标准

### 5.1 样本构成

120 条冻结 JD 应按岗位聚类、T1–T7 技术域、文本复杂度和来源类型分层抽样，避免全部来自同一招聘平台或同一种岗位。

推荐最低覆盖：

| 维度 | 覆盖要求 |
| --- | --- |
| 岗位聚类 | 不少于 12 个聚类，每个聚类 5–15 条 |
| T1–T7 | 每个主技术域至少 10 条，可多标签 |
| 岗位级别 | 实习/初级、中级、高级/专家均有样本 |
| 文本类型 | 标准分段、长文本、短文本、表格化、字段缺失、混合中英文 |
| 来源 | 企业官网和招聘网站均应覆盖 |
| 难例 | 至少 25%，包括别名、缩写、否定表达、加分项和隐含技能 |

现有 3718 条清洗后 JD 可以作为抽样池，但不能直接视为金标准。每条入选样本仍需核对原文、来源、技术词和证据位置。

## 6. 简历解析金标准

### 6.1 格式分布

100 份冻结简历建议按以下格式构成：

| 格式 | 数量 | 重点 |
| --- | ---: | --- |
| 文本 PDF | 25 | 常规段落与双栏版式 |
| 扫描 PDF | 15 | OCR、旋转、低清晰度和页眉干扰 |
| DOCX | 20 | 表格、项目符号和多级标题 |
| TXT/粘贴文本 | 15 | 无版式、分隔符不统一 |
| 复杂 PDF | 15 | 多栏、图标、时间轴和中英混排 |
| 空缺/异常样本 | 10 | 缺联系方式、无技能区、损坏或不支持文件 |

正式测试简历优先使用经过授权的脱敏数据或团队编写的合成简历。当前产业人才库不能替代简历测试集，也不得直接拼装为公开简历。

### 6.2 简历金标准字段

```json
{
  "profile_id": "profile_test_0001",
  "resume_file": "resume_test_0001.pdf",
  "file_type": "pdf_text",
  "target_job_titles": ["机器人感知算法工程师"],
  "education": [
    {"degree": "硕士", "major": "控制科学与工程", "start": "2022-09", "end": "2025-06"}
  ],
  "experiences": [
    {"type": "project", "role": "算法开发", "start": "2024-03", "end": "2024-12"}
  ],
  "skills": [
    {"term_id": "tech_cpp", "level": "applied", "evidence_page": 1, "evidence_text": "使用C++完成……"}
  ],
  "unsupported_inferences": ["外向型人格", "团队领导能力"],
  "annotation_status": "adjudicated"
}
```

性格、发展意愿等 LLM 灵活画像不宜采用逐字匹配作为核心准确率。它们应拆成两类：

- 用户明确陈述且有证据的事实，可纳入结构化金标准；
- 模型归纳或推断的内容，只进行证据充分性、无依据陈述率和专家质量评分。

## 7. 人岗匹配金标准

### 7.1 主任务定义

为了给官方“匹配准确率”一个可复核定义，首版采用岗位—求职者三分类：

| 标签 | 定义 |
| --- | --- |
| `A_STRONG_FIT` | 必备能力覆盖充分，关键差距不影响胜任，级别和经历基本匹配 |
| `B_PARTIAL_FIT` | 有明显可补齐差距，具备相邻能力或潜力，但不能直接视为完全胜任 |
| `C_NOT_FIT` | 核心能力、工作方向或级别存在结构性不匹配 |

构造 300 对样本，建议三类各 100 对。样本中至少三分之一使用“表面关键词相似但语义不适配”或“关键词不完全重合但能力可迁移”的困难负例/正例，防止指标被简单关键词命中抬高。

### 7.2 匹配标注模板

```json
{
  "pair_id": "match_test_0001",
  "profile_version_id": "profile_test_0001_v1",
  "job_version_id": "job_robot_perception_v3",
  "gold_label": "B_PARTIAL_FIT",
  "required_skill_coverage": 0.72,
  "strength_term_ids": ["tech_cpp", "tech_point_cloud"],
  "gap_term_ids": ["tech_ros2", "tech_cuda"],
  "blocking_gaps": ["tech_ros2"],
  "transferable_evidence": ["从PCL项目经验迁移到机器人三维感知"],
  "seniority_fit": "match",
  "expert_rationale": "基础方向一致，但缺少机器人中间件的项目证据。",
  "annotator_agreement": "resolved"
}
```

除 300 对分类样本外，建议再构造 30 个画像查询，每个画像对应 10 个岗位版本的专家排序，用于报告 NDCG@5。分类准确率是官方主指标，排序指标作为产品真实性补充。

## 8. 新岗位闭环场景包

### 8.1 场景组成

每个新岗位场景应包含：

1. 至少三类来源中的多条材料；
2. 技术词与 T1–T7、L1–L4 映射；
3. 已验证技术里程碑；
4. 相关真实 JD 与现有岗位覆盖率；
5. 推演输入参数和算法版本；
6. 各子分数、阈值、证据和反证；
7. 机械生成岗位卡片；
8. LLM 优化版本及字段级修改记录；
9. 人工审核结论；
10. 发布后的岗位版本、标准 JD、图谱节点和边；
11. 后续真实 JD 归入该新岗位的验证样本。

### 8.2 建议样例

首个候选场景可暂定为“机器人世界模型数据工程师”，仅作为测试设计名称，最终是否成立必须由真实数据和专家审核决定。

```yaml
scenario_id: emerging_job_001
title_hypothesis: 机器人世界模型数据工程师
as_of_date: 2026-08-01
inputs:
  source_ids: [source_001, source_002, source_003, source_004]
  milestone_ids: [milestone_001, milestone_002]
  technology_term_ids: [tech_world_model, tech_robot_dataset, tech_simulation]
  related_jd_ids: [jd_0101, jd_0102, jd_0103]
expected:
  candidate_generated: true
  evidence_count_min: 3
  independent_source_groups_min: 2
  manual_review_required: true
  published_as_real_job_before_approval: false
```

这个样例必须同时设置反例：如果里程碑未验证、来源实际均为同一稿件转载，或真实 JD 覆盖不足，系统应降低分数并进入待审核，而不是强行生成正式岗位。

## 9. 既有岗位能力更新场景包

建议首个既有岗位场景使用“机器人算法工程师”或现有数据中样本量充足的岗位聚类。

场景至少包含两个时间窗：

- `T0`：历史 JD 形成的岗位能力基线；
- `T1`：新增一批带时间戳 JD 后的能力更新；
- 可选 `T2`：用于验证持续升温、短期异常和长期衰退的区别。

期望结果需分别标注：

| 结果 | 判定依据 |
| --- | --- |
| 新增能力 | 新时间窗达到频次、来源多样性和持续性门槛 |
| 重要度上升 | 岗位簇内出现频次或覆盖率显著提高 |
| 近期活跃 | 最近若干 JD 高频触发，决定图谱颜色深浅 |
| 长期重要 | 较长时间窗内稳定高频，决定图谱节点距离 |
| 衰退候选 | 长期未出现且不是采集缺失导致 |
| 删除能力 | 必须人工确认，不能仅凭短期未出现自动删除 |

样例断言：新 JD 加入后，目标能力关系版本发生变化；旧版本仍可追溯；同一能力的“长期重要度”和“近期活跃度”不会被合并成一个分数。

## 10. 图谱与 45 天热力测试集

固定构造连续 45 天的逐日技术词触发记录，覆盖 T1–T7 和边界日期。模板如下：

```csv
event_date,term_id,t_domain,level,job_cluster_id,source_material_id,trigger_count,is_verified
2026-06-18,tech_ros2,T3,L3,cluster_robot_control,material_0001,2,true
2026-06-19,tech_ros2,T3,L3,cluster_robot_control,material_0002,1,true
```

需要验证：

- 默认视图只使用 L2 标准技术点；
- 全局模式显示 21 行 × 15 格，并按每三行对应一个技术域；
- 单技术域筛选后展示该域 L2 技术词过去 45 天触发频次；
- 第 45 天包含、第 46 天排除，时区统一为 Asia/Shanghai；
- 未验证候选默认不进入正式热力统计；
- 三类图谱对 T1–T7 使用同一颜色映射；
- 聚类图距离表示长期重要度，颜色深浅表示近期活跃度；
- 全局岗位—能力图只连接岗位聚类与其重要能力。

同时保存期望节点表、期望边表和期望网格聚合表，避免仅通过截图人工判断。

## 11. 数据治理、幻觉和安全测试集

建议的 80 个样本分布：

| 类型 | 数量 | 期望行为 |
| --- | ---: | --- |
| 完全重复与近重复 JD | 15 | 合并或降权，不重复增加能力热度 |
| 同源转载与伪多源 | 10 | 识别复制关系，不按独立证据累计 |
| 过期或无发布日期材料 | 10 | 标记时效风险，不直接影响近期趋势 |
| 来源冲突 | 10 | 保存冲突并进入审核，不静默择一 |
| 缺证据诱导生成 | 10 | 拒绝发布或输出低置信候选 |
| 技术营销夸大 | 5 | 降低来源权重，要求工程任务证据 |
| Prompt 注入文本 | 10 | 不执行材料中的指令，不泄露系统提示 |
| 损坏、超大或伪装文件 | 10 | 安全拒绝并记录明确错误 |

幻觉测试至少报告：

- 无证据技术词率；
- 无证据岗位职责率；
- 无证据匹配理由率；
- 冲突材料静默发布率；
- 伪多源误判率。

其中“静默发布率”目标应为 0；无法确认的内容应进入人工审核，而不是为了召回率直接发布。

## 12. 工程测试夹具

工程测试数据与业务评测金标准分开，避免为了提高代码覆盖率而污染准确率口径。

| 层次 | 固定数据 |
| --- | --- |
| 单元测试 | 单个技术词、边界字符串、分数阈值、时间衰减、状态机和权限样本 |
| 仓储测试 | 唯一键冲突、幂等导入、事务回滚、版本并发和 Outbox 样本 |
| 集成测试 | 原始材料→候选事实→审核→正式 JD→聚类→图谱完整小数据集 |
| 契约测试 | 正常、空结果、分页、非法字段、异步任务失败和错误码样本 |
| 端到端测试 | 新岗位闭环、人岗匹配闭环各一套稳定账号和数据 |
| 性能测试 | 1 万 JD、2 千技术词、100 岗位簇、5 千画像和 45 天事件合成数据 |
| 恢复测试 | 重复消息、Worker 中断、模型超时、数据库暂时不可用和重试样本 |

性能合成数据只能用于性能和容量测试，不进入准确率统计，也不能冒充真实业务数据。

## 13. 指标口径建议

### 13.1 JD 解析主指标

建议以固定权重综合得分回应官方“准确率”，同时完整报告分项：

```text
JD解析综合得分 =
  15% × 岗位名称规范化准确率
+ 20% × 职责要点F1
+ 30% × 必备技能F1
+ 15% × 加分技能F1
+ 10% × T/L分类准确率
+ 10% × 级别与场景字段得分
```

目标为综合得分 ≥90%，且必备技能 Recall 不应低于 90%。权重必须在冻结测试集运行前确定。

### 13.2 简历提取主指标

```text
简历提取综合得分 =
  15% × 基本字段准确率
+ 50% × 标准技能集合F1
+ 15% × 教育/经历事件F1
+ 20% × 证据定位准确率
```

目标为综合得分 ≥90%，另按文件格式分别报告，不能用大量简单 TXT 样本掩盖扫描 PDF 的低表现。

### 13.3 人岗匹配主指标

- 主指标：三分类 Accuracy，目标 ≥90%；
- 必报：Macro-F1、混淆矩阵和各类别样本数；
- 辅助：差距项 micro-F1、NDCG@5、专家排序一致率；
- 可信性：匹配解释的无依据陈述率。

所有指标报告必须保存代码版本、数据版本、技术词版本、模型名称、提示词版本、参数、运行时间和随机种子。

## 14. 标注与冻结流程

1. 先编写标注规范并选择 10–20 条进行试标；
2. 统计分歧，修改规范，不修改样本答案来迎合系统输出；
3. 两名标注者独立标注关键测试样本；
4. 冲突由第三名标注者或领域专家裁决；
5. 类别任务报告 Cohen's Kappa，集合任务报告 Jaccard/F1 一致性；
6. 建议类别一致性 Kappa ≥0.80 后再冻结；
7. 生成清单、版本、文件哈希和冻结标签；
8. 冻结测试答案不得用于提示词、规则或模型调整；
9. 开发阶段只允许查看开发集答案和冻结测试集的聚合错误类型；
10. 最终提交时导出可供评审复跑的输入、金标准、脚本和报告。

如果比赛提交需要公开金标准，可以在最终冻结后发布；开发期间仍需通过版本标签、哈希和变更记录证明测试答案没有参与调参。

## 15. 隐私、版权与发布分级

| 级别 | 允许内容 | 发布方式 |
| --- | --- | --- |
| `public_synthetic` | 完全合成的 JD、简历和画像 | 可随源码公开 |
| `public_deidentified` | 已授权且去除个人/企业敏感标识的样本 | 可随评测包公开 |
| `restricted_research` | 含个人信息或受协议限制的原始材料 | 不进入公开仓库，只保存索引和哈希 |
| `source_reference_only` | 可公开访问但不适合重新分发全文的网页 | 保存 URL、采集元数据和必要证据摘要 |

测试简历不得包含真实姓名、电话、邮箱、身份证号、精确住址和未经授权的个人经历。测试日志、截图、导出文件和演示视频同样遵守该规则。

## 16. 现有数据的可用性

| 现有数据 | 在测试体系中的角色 | 不能直接承担的角色 |

## 18. 当前需要团队确认的三项决策
